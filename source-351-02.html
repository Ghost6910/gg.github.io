351 บท 2: Application Layer, Web, DNS, P2P และ Socket

เปิดบทนี้ในเล่มรวม

สถาปัตยกรรมและบริการที่แอปต้องการ

Client-server ให้ server พร้อมให้บริการและ client เริ่มติดต่อ ส่วน P2P ให้ peer มีบทบาทรับ/ให้ข้อมูลและอาจเข้าหรือออกระบบบ่อย การมี server ช่วยค้น peer ไม่ทำให้ทุก byte ต้องผ่าน server นั้นเสมอ ต้องมองทั้ง control และ data path

แอปเลือกรูปบริการจาก data integrity, throughput, timing และ security เช่นไฟล์ต้องครบแต่ไม่จำเป็นต้องถึงทุกส่วนทันที ส่วนการคุยเสียงให้ความสำคัญเวลาตอบโต้ TCP/UDP ที่มีในสไลด์ให้บริการต่างกัน แต่ไม่มีตัวใดรับประกัน delay ตายตัวบน Internet โดยลำพัง

Socket และการระบุ Process

Socket คือประตูระหว่างโปรแกรมกับ transport แอปส่ง/รับผ่าน API แล้ว OS จัดการ protocol stack IP ระบุ host/interface ส่วน port ช่วยระบุ service endpoint การรู้ IP เครื่องอย่างเดียวไม่บอกว่าจะส่งให้โปรแกรมไหน

ตัวอย่าง TCP server มี listening socket รอรับ แล้วสร้าง connected socket ต่อ client ที่รับเข้ามา Listening socket ไม่ใช่ช่องส่งข้อมูลของทุก connection รวมกันแบบไร้การแยก Client หลายตัวใช้ destination port เดียวกันได้เพราะ connection มี tuple แยกกัน

Web, Mail และ DNS ในหนึ่งสถานการณ์

เมื่อพิมพ์ URL เครื่องแยกชื่อ host แล้วใช้ DNS หา address หากยังไม่มี cache จากนั้นเชื่อม transport และส่ง HTTP ไปขอ resource ถ้ามี objects เพิ่มก็ขอตามความจำเป็น ความสำเร็จแต่ละขั้นต่างกัน: DNS ตอบได้แต่ server ปิด port ก็เปิดหน้าไม่ได้

Mail มี user agents, servers และ protocol ส่ง/อ่านแยกหน้าที่ ทบทวน HTTP ในบท 27, DNS ในบท 25 และ SMTP/POP3/IMAP ในบท 26 เพื่อไม่สลับว่าตัวไหน push ข้อความหรือค้นชื่อ

Cache Hit Ratio และเวลาเฉลี่ย

ถ้า hit ratio h=0.4 เวลาเมื่อ hit=0.01 s และ miss=2 s ในแบบเฉลี่ยสองกรณีที่กำหนด จะได้ E[T]=0.4×0.01+0.6×2=1.204 s แต่ต้องชัดว่าค่า miss รวมการเข้าถึง cache แล้วหรือไม่ หากยังไม่รวมต้องเพิ่มอย่างเหมาะสม ไม่บวกซ้ำตามความเคยชิน

Cache ช่วยลดการใช้ access link และลด queue ที่ลิงก์คอขวดได้ ทำให้ผลจริงอาจมากกว่าการลดเวลาคงที่ตาม hit เพียงอย่างเดียว สมมติฐานของโจทย์จึงสำคัญ

P2P File Distribution

ให้ไฟล์ขนาด F bits, server upload us, client i download di และ upload ui สำหรับ N clients เวลาแบบ client-server มีขอบล่าง max(NF/us, F/dmin) เพราะ server ต้อง upload รวม NF และ client ช้าที่สุดต้องดาวน์โหลดครบ

แบบ P2P มีขอบล่าง max(F/us, F/dmin, NF/(us+Σui)) เพราะต้องปล่อยสำเนาอย่างน้อยหนึ่งชุดและทุกคนร่วม upload ได้ นี่เป็นขอบล่างในแบบจำลอง ไม่รับประกันว่า protocol จริงถึงค่านี้เพราะมี overhead และความพร้อมของชิ้นข้อมูล

ตัวอย่าง F=100 Mbits, N=10, us=10 Mb/s, di=5 Mb/s ทุกตัว และ ui=1 Mb/s: client-server ≥max(100,20)=100 s; P2P ≥max(10,20,1000/20)=50 s ให้ใช้หน่วยไฟล์เป็น bits ให้ตรงอัตรา

BitTorrent และ DHT

BitTorrent แบ่งไฟล์เป็น chunks และ peer แลกชิ้นที่มี การเลือกชิ้นแบบ rarest-first ช่วยให้ชิ้นหายากไม่สูญจากกลุ่มง่าย กลไกเลือก peer/ตอบแทนการ upload ช่วยแรงจูงใจ แต่ไม่เท่ากับการรับประกันว่าทุกคนได้ความเร็วเท่ากัน

DHT กระจายการเก็บ mapping ของ key ไปตาม peer ด้วยโครงสร้างที่ค้นต่อได้ตามกติกา ต่างจากการ broadcast ถามทุกเครื่องเพื่อทุก key ประเด็นคือ key placement, lookup และการเปลี่ยนสมาชิก

ลองตอบ: ถ้ามีชื่อเว็บและ IP แล้วต้องรู้ port ด้วยหรือไม่

เฉลยและเหตุผล: ต้องมีบริการปลายทางตาม transport port ซึ่งอาจได้จากค่าปริยายของ scheme หรือระบุใน URL

ลองตอบ: P2P ยิ่ง client เพิ่มเวลาไม่มีวันเพิ่มเลยหรือไม่

เฉลยและเหตุผล: ไม่ การเพิ่ม peer เพิ่มทั้งความต้องการดาวน์โหลดและศักยภาพ upload ผลขึ้นกับอัตราและระบบ การใช้ขอบล่างไม่ใช่การรับประกันระบบจริง

จำให้ได้: แอปคือ process ปลายทาง; socket คือประตู; แยก control/data path และใช้สูตร distribution พร้อมสมมติฐาน

DNS เป็นระบบชื่อแบบลำดับชั้นและกระจายหน้าที่ ช่วยให้แอปค้น resource records ที่ผูกกับชื่อ ไม่ได้มีหน้าที่แปลง URL ทั้งเส้นเป็น IP โดยตรง URL ยังมี scheme, port, path และ query ที่ DNS ไม่ได้แปลให้

โครงสร้างชื่อไล่จาก root ไป TLD และส่วนย่อย เช่น www.example.com ชื่อ domain กับ zone ไม่เท่ากันเสมอ Zone คือส่วนข้อมูลที่มีผู้รับผิดชอบ authoritative ตามการแบ่งมอบอำนาจ อาจมี delegation ไปส่วนย่อย

ขั้นตอน Query

เครื่องผู้ใช้ถาม recursive resolver ซึ่งอาจตอบจาก cache หรือไล่ถาม root → TLD → authoritative server ตามแบบ iterative Root ไม่จำเป็นต้องรู้ IP ของทุก host แต่ช่วยชี้ต่อไปยังผู้รับผิดชอบที่เหมาะสม

Recursive query ขอให้ปลายทางช่วยหาคำตอบสุดท้าย ส่วน Iterative query อาจได้ referral เพื่อถามต่อ การถามหนึ่งครั้งจากแอปจึงอาจนำไปสู่หลายข้อความ DNS ในโครงข่าย หรือไม่ต้องออกไปไกลเลยถ้า cache ยังใช้ได้

ลองตอบ: TTL=300 ใน DNS เท่ากับผ่าน router ได้ 300 ตัวหรือไม่

เฉลยและเหตุผล: ไม่ เป็นเวลา cache หน่วยวินาทีตาม record ไม่ใช่ hop limit ของ IP

จำให้ได้: DNS ค้น records ของชื่อ ไม่แปล URL ทั้งเส้น; แยก recursive/iterative และ cache/authoritative

แปลและเรียบเรียง Remote Login

Remote login ทำให้ผู้ใช้เข้าถึงบริการคำสั่งบนเครื่องอีกแห่ง สไลด์ยก TELNET ซึ่งจัดรูป terminal ด้วยแนวคิด Network Virtual Terminal การเข้าใจรูปแบบ terminal ช่วยอธิบายว่าทำไมเครื่องต่างระบบยังแลกข้อมูลควบคุมกันได้

TELNET แบบดั้งเดิมส่งข้อมูลโดยไม่ให้การเข้ารหัสแบบ SSH จึงให้แยกการสาธิต protocol ในสไลด์จากการนำไปใช้งานจริง SSH เป็นโปรโตคอลคนละตัว ไม่ใช่เปิดตัวเลือกในข้อความ TELNET แล้วกลายเป็นสิ่งเดียวกัน

E-mail: ใครส่งและใครดึง

User agent ใช้อ่าน/เขียนอีเมล Mail server มี mailbox และ queue SMTP ใช้ส่งจาก client ที่ยื่นส่งไป server และส่งระหว่าง server ส่วน POP3/IMAP ใช้เข้าถึงกล่องข้อความตามรูปแบบบริการ

SMTP เป็นแนว push คือฝั่งผู้ส่งริเริ่มส่งไปปลายทาง ส่วนการอ่านเมลเป็นอีกขั้น IMAP เก็บสถานะและจัดการกล่องข้อความบน server ได้ละเอียดกว่าแบบการดึงพื้นฐานใน POP3 แต่พฤติกรรมการเก็บ/ลบขึ้นกับโหมด client ด้วย

MIME เพิ่มวิธีอธิบายชนิดเนื้อหา encoding และส่วนแนบเพื่อส่งข้อมูลเกินข้อความพื้นฐาน การ encode เช่น Base64 ไม่ใช่ encryption ผู้ที่อ่านข้อมูลได้ยังถอดกลับได้

FTP

FTP แบบดั้งเดิมแยก control connection จาก data connection Control โดยทั่วไปใช้ TCP 21 ส่วน data ขึ้นกับ active/passive mode Active ให้ server เริ่ม data connection ไป client; Passive ให้ client เชื่อมไป port ที่ server แจ้ง จึงมีผลเมื่อผ่าน NAT/firewall

คำตอบว่า FTP ใช้ port 20 สำหรับข้อมูลทุกกรณีจึงไม่ครบ ต้องบอก active/passive และบริบท ส่วน SFTP เป็นบริการถ่ายโอนผ่าน SSH และ FTPS คือ FTP ที่ใช้ TLS เป็นคนละระบบ

HTTP กำหนดข้อความ request/response ในบริบท HTTP/1.x ที่สไลด์ใช้ จะอธิบายการขนส่งบน TCP และข้อความเชิงบรรทัด ส่วนหลักการที่ต้องรู้คือ method, path, headers, status และ body ไม่ตีความตัวอย่างยุคต้นฉบับเป็นข้อกำหนดทุกเวอร์ชัน

Non-persistent, Persistent และเวลา

ในแบบ non-persistent ที่คิดหนึ่ง object ต่อ TCP connection ต้องใช้ประมาณ 1 RTT สร้าง TCP + 1 RTT ส่ง request และรอ response เริ่มต้น + เวลาส่ง object จึงได้ 2RTT+L/R เมื่อไม่คิด DNS และปัจจัยอื่น

ถ้า RTT=80 ms และ object 100 kB บนลิงก์ 10 Mb/s เวลาส่ง=100,000×8/10,000,000=80 ms จึงได้ประมาณ 240 ms สำหรับหนึ่ง object ตามสมมติฐานนี้ Persistent ใช้ connection เดิมซ้ำ ลดการสร้าง connection แต่เวลาทั้งหน้าแปรตามการเรียก object และ concurrency

กลับสารบัญ ↑

State, Cookies และ Cache

HTTP stateless หมายถึงตัว protocol ไม่บังคับให้จำบริบท request เดิมทุกครั้ง แอปยังมี state ได้ด้วย cookie/session Cookie ช่วยส่งค่าที่ server ให้กลับใน request ถัดไป ไม่จำเป็นต้องเก็บรหัสผ่านตรง ๆ และไม่ใช่สิ่งเดียวกับ cache

Cache เก็บ representation เพื่อตอบเร็วและลดโหลด Conditional request เช่น If-Modified-Since หรือ If-None-Match ช่วยตรวจความใหม่ Response 304 ไม่มี representation body ใหม่แบบ 200 ทั่วไป ต้องมีของเดิมที่ cache ใช้ได้

ลองตอบ: 404 แปลว่าไม่มี Internet หรือไม่

เฉลยและเหตุผล: ไม่ 404 เป็น response จากบริการที่ประมวลผล HTTP ได้และบอกว่าไม่พบ resource ตามคำขอ การเชื่อมเครือข่ายกับการมี resource เป็นคนละเรื่อง

ลองตอบ: Stateless ทำ login ไม่ได้หรือไม่

เฉลยและเหตุผล: ทำได้ แอปจัด state โดย token/cookie และข้อมูล session ของตน โปรโตคอล stateless ไม่ได้ห้ามแอปมีความจำ

จำให้ได้: HTTP request/response; เวลาแบบพื้นฐาน 2RTT+ส่งข้อมูล; cookie ≠ cache; 304 ≠ error ข้อมูลหาย

แปลและเรียบเรียง Process-to-process

Transport เชื่อมการสื่อสารระหว่าง process ต่างจาก network layer ที่ขน packet ระหว่าง host/interface Port ระบุปลายทาง transport ส่วน socket เป็นจุดเชื่อมที่โปรแกรมใช้ส่งรับข้อมูล TCP connection ในแบบพื้นฐานแยกด้วย source IP/port และ destination IP/port

UDP มี header 8 bytes ได้แก่ source port, destination port, length และ checksum ไม่มีการตั้ง connection ไม่มี reliability หรือ congestion control ที่ UDP จัดให้เอง แอปเลือกเพิ่มกลไกเองได้ จึงไม่ควรอธิบายว่าแอปบน UDP ทำ reliability ไม่ได้

TCP เป็น byte stream ที่เชื่อถือได้และเรียงลำดับ ไม่รักษาขอบเขตข้อความแอป เช่นส่งสองครั้งไม่ได้รับประกันว่าปลายทาง recv จะได้สองก้อนเท่ากัน แอปต้องจัด framing ของข้อความเอง

TCP sequence และ ACK แบบละเอียด

TCP sequence number ระบุหมายเลข byte ไม่ใช่หมายเลข segment สมมติ segment เริ่ม Seq=1000 มี payload 200 bytes ครอบคลุม 1000–1199 ถ้าผู้รับได้ครบต่อเนื่องจะตอบ ACK=1200 ซึ่งหมายถึงคาดหวัง byte ถัดไป

Cumulative ACK หมายถึงยืนยัน byte ก่อนหน้าอย่างต่อเนื่อง ถ้าขาดช่วง แม้มีข้อมูลถัดไปถึงแล้ว ACK อาจยังชี้ byte แรกที่ขาด การส่งซ้ำมี timer และ fast retransmit ตามกลไกที่ใช้ Checksum ตรวจผิดไม่ได้ทำหน้าที่แทน sequence หรือ timer

การเปิดและปิด Connection

Three-way handshake: Client ส่ง SYN Seq=x; Server ตอบ SYN+ACK Seq=y, ACK=x+1; Client ตอบ ACK=y+1 เพราะ SYN ใช้หนึ่ง sequence number ช่วยให้สองฝ่ายตกลงเลขเริ่มต้นและรับรู้การสื่อสารสองทาง

การปิดแต่ละทิศใช้ FIN ซึ่งใช้หนึ่ง sequence number เช่นกัน TCP full-duplex จึงอาจปิดการส่งฝั่งหนึ่งก่อนอีกฝั่ง FIN กับ RST ทำหน้าที่ต่างกัน และ state เช่น TIME_WAIT มีเหตุผลด้านข้อมูลเก่าและการตอบรับท้าย

Flow control กับ Congestion control

rwnd คือพื้นที่รับที่ผู้รับประกาศเพื่อไม่ให้ buffer ฝั่งรับล้น ส่วน cwnd จำกัดข้อมูลค้างบนเครือข่ายเพื่อคุม congestion ข้อมูลที่ส่งค้างได้ถูกจำกัดทั้งสองด้าน ในแบบพื้นฐานต้องอยู่ภายใต้ min(rwnd,cwnd) หักข้อมูลที่ส่งไปแล้วยังไม่ ACK

SCTP ที่สไลด์แนะนำเป็น transport แบบ message-oriented มีแนวคิด multistreaming และ multihoming จึงแยกจาก TCP byte stream อย่านำคำว่า multi-stream มาอธิบายว่า TCP รักษาขอบเขตข้อความได้

ลองตอบ: Seq=700 ส่ง 50 bytes ผู้รับครบต้อง ACK เท่าไร

เฉลยและเหตุผล: ACK=750 และ segment ข้อมูลถัดไปเริ่มที่ 750 หากไม่มี SYN/FIN ในช่วงนั้น

ลองตอบ: Port เดียวกันทำไม server รับหลาย client พร้อมกันได้

เฉลยและเหตุผล: เพราะ TCP connection มีคู่ที่อยู่และ port ทั้งสองฝั่ง ต่าง client จึงแยก connection ได้แม้ destination port เหมือนกัน

จำให้ได้: UDP 8-byte header; TCP เป็น byte stream; ACK คือ byte ถัดไป; rwnd ป้องกันผู้รับ, cwnd ป้องกันเครือข่าย
