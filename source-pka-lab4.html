เปิดบทนี้ในเล่มรวม

ขอบเขตคู่มือและสิ่งที่ตรวจได้

โฟลเดอร์มีไฟล์กิจกรรม .pka 9 ไฟล์ คู่มือนี้เรียบเรียงแนวทำ ความหมายของขั้นตอน และการตรวจผลตามหัวข้อที่ระบุในชื่อกิจกรรม โดยยังไม่ได้ถอด topology, instruction ภายใน หรือ answer network ของไฟล์ .pka จึงไม่อ้างว่าเลข IP, รหัสผ่าน, interface หรือคำสั่งตัวอย่างเป็นคำตอบตรงของกิจกรรมที่ล็อกไว้

เมื่อเปิดกิจกรรมให้ใช้ค่าใน Addressing Table, topology และ instructions ของไฟล์เป็นหลัก ตัวอย่างที่ระบุว่า “สมมติ” ใช้สอนแนวคิดเท่านั้น ส่วนหัวข้อ Check Results ของ Packet Tracer เป็นเกณฑ์ตรวจเฉพาะกิจกรรม ไม่ใช่สิ่งที่คู่มือนี้ยืนยันว่าได้คะแนนครบแล้ว

กลับสารบัญ ↑

ขั้นตอนทำงานทุก Lab

  1. เปิดสำเนากิจกรรมและอ่าน Objectives, Addressing Table กับ Instructions ก่อนแก้ค่า
  2. บันทึกอุปกรณ์ interface, IP/mask, gateway, สายเชื่อม และบริการที่โจทย์กำหนด
  3. เช็ก Physical/Link ก่อน IP แล้วทดสอบทีละชั้น อย่าเปลี่ยนหลายค่าโดยไม่รู้ว่าอะไรแก้อาการ
  4. ใน Simulation mode เลือกชนิด event ที่ต้องการดู แล้วเดินทีละเหตุการณ์ เปรียบเทียบ header ก่อนและหลังอุปกรณ์
  5. จดคำสั่งที่ใช้ ผลที่คาด และผลที่เห็นจริง แยกค่าตามโจทย์จากค่าตัวอย่าง
  6. บันทึกเป็นชื่อใหม่เมื่อทดลองเส้นทางหรือปิดลิงก์ และใช้ Check Results ตามที่กิจกรรมเปิดให้ตรวจ

5.5.2.2 — Examining a Route

เปิดบทนี้ในเล่มรวม

แปลชื่อและเป้าหมายติว

Examining a Route = ตรวจสอบเส้นทาง เป้าหมายคือเชื่อมผล traceroute/tracert กับ routing table และเส้นทางข้อมูลที่เห็น ไม่ใช่จำว่า hop ที่สองต้องเป็นเลขใดโดยไม่ดู topology

กลับสารบัญ ↑

ขั้นทดลอง

  1. ใช้ ping ปลายทางจากจุดที่โจทย์กำหนดก่อนบันทึกอาการ
  2. ใช้ tracert บน PC หรือ traceroute บน router ตามสิ่งที่อุปกรณ์รองรับ
  3. เทียบแต่ละ hop กับ interface ของ router ใน topology และดูว่าคำตอบอาจมาจาก interface ใด
  4. ที่แต่ละ router ตรวจ route ไปปลายทางโดย longest prefix match และ next hop
  5. ถ้ามี * หรือไม่ตอบ ให้ตรวจ event ว่า probe ไปถึงไหม และ response กลับได้ไหม ไม่เดาว่า hop นั้นเสียแน่นอน
  6. ตรวจเส้นขากลับแยกต่างหาก เนื่องจากเส้นทางไปและกลับไม่จำเป็นต้องเหมือนกัน
กลับสารบัญ ↑

สิ่งที่ต้องเขียนในรายงาน

ระบุต้นทาง ปลายทาง prefix ที่ถูกเลือกในแต่ละ router และเหตุผลที่เลือก ถ้าระบุความหน่วงต้องบอกว่าเป็น RTT ของ probe ถึง hop ไม่ใช่เวลาช่วงลิงก์เดียวเสมอ และค่า RTT อาจไม่เพิ่มอย่างเรียบตามจำนวน hop

ลองตอบ: Hop 3 RTT ต่ำกว่า hop 2 แปลว่าคำนวณผิดเสมอหรือไม่

เฉลยและเหตุผล: ไม่ เวลาแต่ละ probe และการตอบสนองต่างกันได้ ไม่ได้วัดแต่ละลิงก์ด้วยนาฬิกาเดียวอย่างสมบูรณ์

จำให้ได้: Traceroute เป็นหลักฐานการตอบ probe ภายใต้เงื่อนไขทดสอบ ให้เทียบ routing และ topology ร่วมกัน

กลับสารบัญ ↑
