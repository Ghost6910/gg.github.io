# บทอ่านละเอียด: เครือข่ายและ Cloud สำหรับเตรียมสอบ 351

เอกสารนี้ขยายจากหัวข้อในภาพและเอกสารเรียนในโฟลเดอร์เดิม เป้าหมายคือให้อ่านแล้วอธิบายเหตุผลได้ ไม่ต้องอาศัยการจำชื่อเพียงอย่างเดียว คำอังกฤษเก็บไว้เพราะข้อสอบอาจใช้ศัพท์เหล่านั้นโดยตรง ส่วนรายละเอียด Cloud เป็นพื้นฐานทั่วไป เนื่องจากยังไม่มีเอกสาร Cloud ของอาจารย์ในชุดที่อ่าน

**วิธีอ่าน:** อ่านคำอธิบายให้เห็นภาพ → ทำตัวอย่างด้วยตัวเองก่อนดูวิธี → ทวนจุดหลอก → ไปทำข้อกาในหมวดเดียวกัน ข้อสอบฝึกเป็นข้อที่แต่งขึ้น ไม่ใช่ข้อสอบจริง และสัดส่วนในโหมดจำลองไม่ได้ยืนยันจากอาจารย์

## 1. Internet Protocol Stack และ OSI: ส่งข้อมูลหนึ่งครั้ง ใครทำอะไรบ้าง

### 1.1 เริ่มจากเรื่องใกล้ตัว: กดเปิดเว็บหนึ่งหน้า

เมื่อพิมพ์ชื่อเว็บแล้วกด Enter คอมพิวเตอร์ไม่ได้โยน “หน้าเว็บ” ลงสายตรง ๆ แอปต้องสร้างข้อความขอข้อมูล ระบบต้องรู้ว่าจะส่งให้โปรแกรมไหนบนเครื่องปลายทาง จะข้ามเครือข่ายทางใด และจะส่งสัญญาณบนสายหรือคลื่นอย่างไร งานเหล่านี้ต่างกัน จึงแบ่งเป็นชั้น หรือ **Layer**

นึกถึงการส่งพัสดุ คนเขียนจดหมายไม่จำเป็นต้องขับรถส่งเอง และคนขับรถไม่จำเป็นต้องอ่านเนื้อหาจดหมาย แต่ทุกฝ่ายต้องทำตามกติกาที่เข้ากันได้ เครือข่ายก็แยกหน้าที่ลักษณะนี้ การเปรียบเทียบช่วยเห็นภาพ แต่กลไกจริงต้องดู header, address และ protocol ของแต่ละชั้น

**Protocol** คือกติกาว่าข้อความหน้าตาอย่างไร ส่งเมื่อใด รับแล้วต้องทำอะไร เช่น HTTP กำหนด request/response ส่วน TCP กำหนดการนับ byte การตอบรับและการส่งซ้ำ การต่อสายถูกจึงยังไม่พอ หากคู่สื่อสารใช้กติกาไม่ตรงกัน

### 1.2 OSI ทั้ง 7 ชั้น แบบเข้าใจหน้าที่

|ชั้น|คิดเป็นภาษาคน|คำเทคนิคและตัวอย่าง|
|---|---|---|
|7 Application|แอปจะคุยเรื่องอะไรกับอีกฝั่ง|HTTP, DNS, SMTP เป็น protocol ระดับแอป|
|6 Presentation|จัดรูปข้อมูลให้ตีความตรงกัน|การแทนข้อมูล การบีบอัด การเข้ารหัสในเชิงแบบจำลอง|
|5 Session|จัดการบทสนทนาที่กำลังคุยกัน|สร้าง ดูแล และยุติ session ตามหน้าที่ของแบบจำลอง|
|4 Transport|ส่งข้อมูลให้ถูกโปรแกรม และจัดคุณสมบัติการส่ง|TCP, UDP และ port number|
|3 Network|พาข้อมูลข้ามหลายเครือข่าย|IP, packet forwarding และ routing|
|2 Data Link|ส่งข้อมูลไปอีกฝั่งของลิงก์หรือภายใน LAN ตามเทคโนโลยี|Ethernet frame, MAC address, medium access|
|1 Physical|เปลี่ยนบิตให้เป็นสิ่งที่เดินทางผ่านสื่อได้|สัญญาณไฟฟ้า แสง คลื่นวิทยุ หัวต่อและการส่งบิต|

ชั้น Application ไม่ใช่ชื่อเรียกโปรแกรมทุกชนิดบนคอมพิวเตอร์ แต่เป็นหน้าที่และ protocol สำหรับการสื่อสารของแอป ส่วนการวาง TLS ไว้ชั้นใดแบบตายตัวอาจทำให้สับสน เพราะ protocol จริงไม่ได้เข้ากล่อง OSI ได้สมบูรณ์ทุกตัว ใช้แบบจำลองเพื่อเข้าใจหน้าที่ แล้วดูสถาปัตยกรรมจริงประกอบ

### 1.3 แล้ว TCP/IP ทำไมมีทั้ง 4 และ 5 ชั้น

Internet stack แบบที่ใช้สอนบ่อยมี 5 ชั้น คือ Application → Transport → Network → Link → Physical แต่ตำราที่เรียก TCP/IP แบบ 4 ชั้นรวม Link และ Physical เป็น Network access ส่วนหน้าที่ OSI ชั้น 5–7 มักถูกรวมอยู่ฝั่ง Application จึงไม่มีความขัดแย้งถ้าตำราหนึ่งบอก 4 อีกเล่มบอก 5 ต้องอ่านว่าข้อสอบถามแบบจำลองใด

### 1.4 Encapsulation: หุ้มข้อมูลเป็นชั้น ๆ

สมมติ browser มีข้อความ HTTP ระบบจะใส่ TCP header เพื่อระบุ port และข้อมูลควบคุม จากนั้นใส่ IP header เพื่อระบุ IP ต้นทาง/ปลายทาง แล้วหุ้มเป็น Ethernet frame เพื่อส่งบนลิงก์ สุดท้าย Physical เปลี่ยนบิตเป็นสัญญาณ ฝั่งรับทำย้อนกลับ เรียก **Decapsulation**

```text
ข้อมูลแอป
→ [TCP header | ข้อมูลแอป]                         segment
→ [IP header | TCP header | ข้อมูลแอป]             packet
→ [Ethernet header | IP packet | FCS]              frame
→ สัญญาณบนสื่อ                                    bits/signals
```

UDP มักเรียกหน่วยข้อมูลว่า UDP datagram ส่วน IP ก็ใช้คำว่า datagram ได้เช่นกัน ต้องดูบริบท ไม่ใช่เห็นคำว่า datagram แล้วสรุปว่า UDP เท่านั้น

### 1.5 MAC, IP และ Port ต่างกันตรงไหน

**MAC** ใช้ตัดสินใจส่งบนลิงก์ Ethernet/Wi-Fi ตามเทคโนโลยีนั้น **IP** ใช้ระบุปลายทางในเชิงเครือข่ายและส่งข้ามเครือข่าย **Port** ช่วยเลือกบริการหรือ process บนเครื่องปลายทาง ตัวอย่างเช่น ไปเครื่อง 203.0.113.10 แล้วติดต่อ TCP port 443 เพื่อใช้บริการ HTTPS

อย่าท่องว่า MAC คือที่อยู่ “เปลี่ยนไม่ได้” เพราะอุปกรณ์และซอฟต์แวร์อาจเปลี่ยนหรือสุ่ม MAC ได้ และอย่าท่องว่า IP คือที่อยู่ถาวรของคนหนึ่งคน เพราะ IP อาจเปลี่ยน แชร์ผ่าน NAT หรือเป็นหลาย address ต่อ interface

เมื่อส่งไปเว็บที่อยู่นอก subnet เครื่องเราส่ง **IP packet ถึงเว็บเซิร์ฟเวอร์ แต่ Ethernet frame แรกถึง gateway** Router ถอด frame เดิม ลด TTL แล้วหุ้ม frame ใหม่สำหรับลิงก์ถัดไป หากไม่มี NAT หรือการแปลงอื่น IP ต้นทาง/ปลายทางโดยทั่วไปคงเดิม ขณะที่ MAC เปลี่ยนตามลิงก์

### 1.6 Delay กับ Throughput: ช้าเพราะอะไร

- **Processing delay:** เวลาตรวจและประมวลผลข้อมูลที่อุปกรณ์
- **Queueing delay:** เวลารอคิวก่อนส่งต่อ เปลี่ยนตามโหลดและคิว
- **Transmission delay = L/R:** เวลาที่ใช้ผลักบิตทั้งหมดลงลิงก์ L ต้องเป็นบิต และ R เป็นบิตต่อวินาที
- **Propagation delay = d/v:** เวลาที่สัญญาณเดินทางผ่านระยะ d ด้วยความเร็ว v

**ตัวอย่าง:** frame 1,500 bytes บนลิงก์ 10 Mb/s ใช้ transmission delay = 1,500×8 / 10,000,000 = 0.0012 วินาที = **1.2 ms** โดยตัวอย่างนี้ไม่นับ overhead นอกขนาดที่กำหนด ส่วนระยะ 2,000 km ที่ความเร็วสัญญาณ 200,000 km/s มี propagation delay = 0.01 วินาที = **10 ms**

เพิ่ม bandwidth ช่วยลด transmission delay แต่ไม่ได้ทำให้ระยะทางสั้นลง ส่วน throughput คืออัตราที่ส่งข้อมูลได้จริง หากผ่านลิงก์ 100 → 20 → 50 Mb/s แบบอนุกรม เพดานตามแบบจำลองง่าย ๆ คือ 20 Mb/s ก่อนคิด traffic อื่นและ overhead ไม่ใช่ 170 Mb/s

**จุดหลอก:** bit ต่างจาก byte; ms ต่างจากวินาที; ความเร็วลิงก์ไม่เท่ากับ throughput แอป; IP ปลายทางไม่เท่ากับ MAC next hop; TCP/IP ไม่ได้มีจำนวนชั้นเดียวในทุกตำรา

## 2. Application Layer: เว็บ DNS DHCP และ TCP/UDP

### 2.1 แอปไม่ได้คุยกับ “ทั้งเครื่อง” แบบไม่มีปลายทางย่อย

เครื่องเดียวเปิด browser, อีเมล และโปรแกรมคุยพร้อมกันได้ ระบบต้องแยกข้อมูลให้ถูก process การสื่อสารจึงเกี่ยวข้องกับ **socket** และ port IP บอกว่าจะไป interface/เครื่องใด ส่วน port ช่วยบอกว่าจะส่งให้บริการใดในบริบทของ transport protocol

TCP และ UDP มีพื้นที่หมายเลข port แยกกัน TCP 53 กับ UDP 53 จึงไม่ใช่ socket เดียวกัน การระบุ connection TCP ยังใช้คู่ IP/port ของทั้งสองฝั่งร่วมกัน ไม่ใช่ดู destination port ตัวเดียวแล้วแยกทุก connection ได้

### 2.2 TCP: ส่งให้ครบ เรียงให้ถูก แต่ไม่ได้เข้าใจข้อความแอปแทนเรา

TCP ให้บริการ **reliable, ordered byte stream** หากข้อมูลหายสามารถส่งซ้ำ และส่ง byte ให้แอปตามลำดับ แต่ไม่ได้รับประกันว่าการเรียกส่งข้อมูลสองครั้งจะทำให้ฝั่งรับอ่านได้สองก้อนตรงขนาดเดิม แอปต้องออกแบบขอบเขตข้อความเอง เช่น ระบุความยาวหรือใช้ delimiter

TCP เปิด connection ด้วย **SYN → SYN-ACK → ACK** ส่วนการส่งข้อมูลใช้ sequence number, acknowledgment และ timer ช่วยติดตาม สิ่งที่ ACK บอกโดยหลักคือ “byte ถัดไปที่ฉันต้องการคือหมายเลขนี้”

**ตัวอย่าง:** ส่ง Seq=1000 ขนาด 200 bytes จะครอบคลุม byte 1000–1199 หากรับครบต่อเนื่อง ผู้รับตอบ **ACK=1200** ไม่ใช่ 1199 และไม่ใช่ 1 ถ้าส่วนที่เริ่ม 1200 หาย แต่ส่วน 1400 มาถึง cumulative ACK อาจยังชี้ 1200 เพราะข้อมูลก่อนหน้ายังไม่ครบ

**Flow control** ช่วยไม่ให้ส่งเร็วเกิน buffer ของผู้รับ ส่วน **Congestion control** ช่วยปรับอัตราส่งตามความแออัดของเครือข่าย สองเรื่องนี้แก้คนละปัญหา แม้อาจมีผลต่อปริมาณข้อมูลค้างส่งเหมือนกัน

### 2.3 UDP: กลไกน้อย ไม่รับประกันด้วยตัวมันเอง

UDP ส่งเป็น datagram ไม่มี three-way handshake และไม่มี reliability, การจัดลำดับ หรือ congestion control ที่ UDP จัดให้เอง จึงมี header และกลไกน้อยกว่า TCP แต่ไม่ควรสรุปว่า “UDP เร็วกว่าเสมอ” หรือ “แอปบน UDP ส่งแบบเชื่อถือไม่ได้ตลอดไป” เพราะแอปสามารถสร้างการตอบรับ การส่งซ้ำ และกลไกควบคุมของตัวเองได้ เช่น QUIC ใช้ UDP เป็นฐาน

งานเสียง/วิดีโอบางแบบให้ความสำคัญกับเวลามากกว่าการรอข้อมูลเก่าครบ แต่ก็ยังต้องออกแบบการรับมือ loss และ congestion ไม่ใช่ส่งได้ไม่จำกัด

### 2.4 DNS: รู้ชื่อแล้วต้องหา address ก่อน

DNS เป็นระบบข้อมูลชื่อแบบลำดับชั้น ไม่ใช่เว็บเซิร์ฟเวอร์ Browser หรือระบบปฏิบัติการมักถาม resolver และใช้ cache ถ้ามีคำตอบที่ยังใช้ได้ Resolver อาจไปถาม root, TLD และ authoritative server ตามความจำเป็น

|Record|ใช้เก็บอะไร|ข้อควรจำ|
|A|IPv4 ของชื่อ|หนึ่งชื่ออาจมีหลาย address|
|AAAA|IPv6 ของชื่อ|AAAA ไม่ใช่ A จำนวนสี่รายการ|
|CNAME|ชื่อแฝงที่อ้างไปอีกชื่อ|ไม่ได้เก็บ IP โดยตรง|
|MX|Mail exchanger ของโดเมน|ใช้สำหรับเส้นทางการรับอีเมล|
|NS|Nameserver ของ zone|เกี่ยวกับผู้ให้คำตอบ DNS ของส่วนชื่อนั้น|

**DNS TTL** เป็นอายุการเก็บคำตอบใน cache ไม่ใช่ IP TTL ที่ router ลดทุก hop DNS ใช้ UDP และ TCP port 53 ตามกรณี จึงผิดถ้าบอกว่าใช้ UDP เท่านั้น

### 2.5 DHCP: ขอข้อมูลตั้งค่าเครือข่ายอัตโนมัติ

DHCPv4 มักสอนด้วย DORA: **Discover** ถามหาบริการ → **Offer** เสนอค่า → **Request** ขอใช้ข้อเสนอ → **ACK** ยืนยันการเช่า อาจได้ IP, subnet mask, default gateway และ DNS server พร้อมระยะเวลา lease Server ใช้ UDP 67 ส่วน client ใช้ UDP 68

ต้องแยกหน้าที่: DHCP แจก configuration ส่วน DNS ตอบข้อมูลชื่อ หากได้ IP แล้วแต่ DNS ผิด อาจ ping address ได้แต่เปิดด้วยชื่อไม่ได้ และถ้าเครื่องได้ IPv4 link-local 169.254.x.x ในระบบที่รองรับ อาจเป็นเพราะยังไม่ได้ DHCP lease ไม่ใช่หลักฐานว่า Internet พร้อม

### 2.6 HTTP, HTTPS และสถานะที่ควรรู้

HTTP แลกเปลี่ยน **request/response** Client ขอทรัพยากร Server ตอบ status, header และอาจมี body **GET** ขอ representation ของทรัพยากร ส่วน **POST** ส่งข้อมูลให้ปลายทางประมวลผลตามความหมายของ resource การใช้ POST ไม่ได้เข้ารหัสข้อมูลให้เอง

|Status|ภาษาคน|จำให้ถูก|
|200 OK|คำขอสำเร็จตามความหมายของ method|ต้องดู body/บริการด้วย ไม่ใช่รับรองข้อมูลทุกอย่างถูก|
|301 Moved Permanently|ย้ายถาวร|มักมีตำแหน่งใหม่ให้ไปต่อ|
|403 Forbidden|server ปฏิเสธสิทธิ์เข้าถึง|ไม่เหมือน 404|
|404 Not Found|ไม่พบทรัพยากรที่ขอ|ไม่ได้แปลว่าเครื่อง server ไม่มีไฟเลี้ยง|
|500 Internal Server Error|server มีข้อผิดพลาดภายใน|เป็นปัญหาฝั่ง server ตามสถานะ|

HTTP เป็น **stateless** ในเชิง protocol แต่เว็บยังทำระบบล็อกอินได้โดยใช้ cookie, token หรือ session ที่แอปออกแบบ Cookie อาจใช้เก็บตัวระบุ session ไม่จำเป็นต้องเก็บรหัสผ่าน และไม่ใช่การเข้ารหัส

HTTPS ใช้ TLS ปกป้องการสื่อสาร เช่น ความลับและความครบถ้วน พร้อมการตรวจตัวตนตาม certificate และกระบวนการยืนยัน จึงต้องตรวจชื่อโดเมนและความน่าเชื่อถือของ certificate ด้วย แต่เว็บหลอกลวงก็มี HTTPS ได้ การเข้ารหัสไม่ได้รับประกันว่าเจ้าของเว็บพูดความจริง

### 2.7 ตาราง Port ที่ควรทวน

|บริการ|Port โดยทั่วไป|ใช้ทำอะไร|
|HTTP|TCP 80|เว็บไม่ใช้ TLS|
|HTTPS|TCP 443; HTTP/3 ใช้ UDP 443|เว็บที่ปกป้องด้วย TLS; HTTP/3 ทำงานผ่าน QUIC|
|DNS|UDP/TCP 53|ข้อมูลชื่อ|
|DHCPv4|UDP server 67 / client 68|แจก network configuration|

ตัวเลขเหล่านี้เป็นค่าโดยทั่วไป ไม่ใช่การรับประกันว่าผู้ดูแลเปลี่ยนไม่ได้ และอย่าสับสน FTP กับ SFTP ซึ่งเป็นคนละ protocol โดย SFTP ใช้ผ่าน SSH

**จุดหลอก:** DNS ไม่แจก IP แบบ DHCP; ping ผ่านไม่รับรอง HTTP; TCP นับ byte; UDP ไม่ได้ห้ามแอปสร้าง reliability; HTTPS ไม่รับประกันความซื่อสัตย์ของเว็บ

## 3. Routing, Subnet และผังเครือข่าย

### 3.1 Routing กับ Forwarding: วางแผนกับลงมือส่ง

**Routing** เป็นกระบวนการสร้างหรือเรียนรู้เส้นทาง เช่น ผู้ดูแลตั้ง static route หรือ router แลกเปลี่ยนข้อมูลด้วย OSPF ส่วน **Forwarding** คือเมื่อ packet มาถึงแล้ว จะส่งออก interface ไหนและให้ next hop ใด โดยอาศัยเส้นทางที่ติดตั้งแล้ว

นึกถึงการทำตารางรถกับการส่งรถจริง ตารางต้องมีก่อนจึงรู้ว่ารถที่มาถึงควรไปทางไหน Router ไม่จำเป็นต้องเริ่มคำนวณ topology ทั้งโลกใหม่กับทุก packet

### 3.2 IPv4 / Prefix / Mask ต้องอ่านให้เป็น

IPv4 มี 32 บิต แบ่งเขียนเป็น 4 octets เช่น 192.168.1.70 Prefix `/26` หมายถึง 26 บิตแรกเป็น network part เหลือ 6 บิตสำหรับ host part Mask จึงเป็น 255.255.255.192 เพราะ octet สุดท้ายคือ 11000000

|Prefix|Mask|จำนวน address ทั้งหมด|Usable hosts ของ subnet IPv4 ปกติ|
|---|---|---|---|
|/24|255.255.255.0|256|254|
|/25|255.255.255.128|128|126|
|/26|255.255.255.192|64|62|
|/27|255.255.255.224|32|30|
|/28|255.255.255.240|16|14|
|/29|255.255.255.248|8|6|
|/30|255.255.255.252|4|2|

สูตรจำนวน address คือ **2^(32−prefix)** ส่วน usable ของ subnet แบบทั่วไปลบ 2 เพราะสงวน network address กับ directed broadcast address อย่าใช้สูตรลบ 2 กับทุกกรณี: /31 สำหรับ point-to-point มีข้อยกเว้น และ /32 แทน address เดี่ยว

### 3.3 ทำโจทย์ Subnet ทีละขั้น: 192.168.1.70/26

1. `/26` ทำให้ octet สุดท้ายของ mask เป็น 192
2. Block size = 256−192 = **64** จึงมีช่วง 0–63, 64–127, 128–191, 192–255
3. เลข 70 อยู่ช่วง **64–127** จึงได้ network = **192.168.1.64**
4. ค่าสุดท้ายของช่วงคือ broadcast = **192.168.1.127**
5. ใช้งาน host ปกติได้ **192.168.1.65–126** รวม **62 เครื่อง**

ที่บอกว่า `/26` กระโดดทีละ 64 ใน octet สุดท้ายเป็นวิธีลัดสำหรับกรณีนี้ ถ้าโจทย์ใช้ /20 ต้องคิดที่ octet ที่สาม ไม่เอาวิธีจำ octet สุดท้ายไปแทนตรง ๆ หลักทั่วไปคือ **Network = IP AND subnet mask**

### 3.4 ต้องการ 50 เครื่อง เลือก subnet เท่าไร

หา host bits h ที่ทำให้ **2^h−2 ≥ 50** ถ้า h=5 ได้ 30 ไม่พอ ถ้า h=6 ได้ 62 พอ จึงใช้ prefix 32−6 = **/26** คำว่า “เล็กที่สุดที่พอ” หมายถึงเลือก block ที่ไม่ใหญ่เกินจำเป็น ไม่ใช่เลือก prefix ตัวเลขน้อยที่สุด

หากแบ่ง 192.168.1.0/24 เป็น /26 จะเพิ่ม network bits 2 บิต ได้ **4 subnets** แต่ละ subnet มี 64 address และ 62 usable hosts อย่าสับสนจำนวน subnet กับจำนวน host

### 3.5 เครื่องตัดสินว่าอีกเครื่องอยู่ subnet เดียวกันได้อย่างไร

Host นำ IP ตนเอง AND mask แล้วเปรียบเทียบกับ IP ปลายทาง AND mask ตาม routing configuration ของตน ถ้าเป็นปลายทาง on-link ก็ส่งตรงผ่านลิงก์ เช่น ARP หา MAC ของเครื่องนั้นใน IPv4 ถ้าต้องผ่าน gateway จะ resolve MAC ของ gateway แทน

ตัวอย่าง A=192.168.1.70/26 กับ B=192.168.1.90 อยู่ช่วง 64–127 เหมือนกัน แต่ C=192.168.1.140 อยู่ช่วง 128–191 จึงเป็นอีก subnet แม้สาม octets แรกจะเหมือนกัน คำว่า “192.168.1 เหมือนกันจึงวงเดียวกัน” ผิดถ้าไม่ดู mask

Default gateway โดยทั่วไปต้องมี address ที่ host เข้าถึงบนลิงก์ของตนได้ การตั้ง gateway เป็น address ของเว็บ server ระยะไกลจึงไม่ทำให้เครื่องข้ามเครือข่ายได้เอง

### 3.6 เลือก Route: Longest Prefix, AD และ Metric คนละขั้น

**ตอน forwarding:** เทียบ IP ปลายทางกับ prefix ที่ติดตั้งใน routing table แล้วเลือก **Longest Prefix Match** คือ match บิตต้นได้ยาวที่สุด เช่นปลายทาง 10.1.2.5 match ทั้ง 10.0.0.0/8 และ 10.1.2.0/24 ให้เลือก /24 เพราะจำเพาะกว่า

**ตอนพิจารณาติดตั้ง route ไป prefix เดียวกันจากต่างแหล่ง:** Cisco ใช้ **Administrative Distance — AD** เป็นค่าความน่าเชื่อถือของแหล่ง route โดยทั่วไปค่าน้อยได้รับเลือกก่อน ตัวอย่าง connected 0, static 1, OSPF 110, RIP 120 เป็นค่าเริ่มต้นที่ตั้งเปลี่ยนได้

**ภายใน routing protocol:** ใช้ **Metric** ตามกติกาของ protocol เพื่อเปรียบเทียบเส้นทาง เช่น RIP ใช้ hop count, OSPF ใช้ cost ไม่ควรเอา metric คนละ protocol มาเทียบเลขตรง ๆ แล้วสรุปว่าใครดีกว่า

**โจทย์หลอก:** ในตารางมี /0 ค่า AD 1 กับ /24 ค่า AD 110 และปลายทาง match ทั้งคู่ การ forwarding เลือก **/24** ไม่ใช่ /0 เพราะ AD ไม่ได้เอามาข้ามกติกา longest prefix ระหว่าง prefix ต่างกัน

### 3.7 Static, Dynamic และ Default Route

Static route ผู้ดูแลกำหนดเอง เหมาะกับเส้นทางที่เรียบง่ายหรือมีเงื่อนไขที่ต้องการกำหนดชัด แต่เมื่อ topology เปลี่ยนอาจต้องแก้เอง Dynamic routing เช่น OSPF/RIP ช่วยเรียนรู้และปรับเส้นทางตามกลไกของ protocol แต่มีการตั้งค่า การแลกเปลี่ยนข้อมูล และเวลา convergence

**Default route = 0.0.0.0/0** เป็นทางเลือกเมื่อไม่มี route ที่จำเพาะกว่า ไม่ได้แปลว่าถ้ามี default แล้วจะเข้าถึงทุกปลายทางได้แน่นอน เพราะ next hop, เส้นทางถัดไป, route ขากลับ หรือ policy อาจมีปัญหา

RIP เป็น distance-vector ใช้ hop count และมอง 16 hops ว่า unreachable ส่วน OSPF เป็น link-state ใช้ฐานข้อมูล link state และคำนวณเส้นทางตาม cost ต้องอ่าน scope และการตั้งค่าจริงประกอบ

### 3.8 อ่านผังเครือข่ายให้ถูกก่อนแตะคำสั่ง

```text
PC-A —— Switch-A —— R1 —— R2 —— Switch-B —— PC-B
       LAN A           Transit link          LAN B
    192.168.1.0/24    10.0.0.0/30       192.168.2.0/24
```

แต่ละช่วงที่คั่นด้วย router เป็นคนละเครือข่ายตามการออกแบบนี้ Switch ไม่ได้สร้าง subnet ใหม่ทุกพอร์ต ส่วน interface ของ router ที่อยู่แต่ละฝั่งต้องมี address ที่ตรงกับวงนั้น หาก A จะคุย B ต้องมี gateway ของ A, route ที่ R1 ไป LAN B, การเชื่อมต่อระหว่าง router และเส้นทางตอบกลับจาก B/R2 ไป LAN A ครบ

|Topology|มองภาพอย่างไร|ข้อพิจารณา|
|Star|ทุกโหนดต่อจุดกลาง|สายปลายทางขาดกระทบโหนดนั้น แต่ศูนย์กลางล่มกระทบวง|
|Bus|ใช้ backbone ร่วม|ปัญหาสื่อร่วมอาจกระทบหลายโหนด|
|Ring|โหนดเชื่อมเป็นวง|การรับมือสายขาดขึ้นกับระบบและวงสำรอง|
|Full mesh|ทุกคู่มีลิงก์ตรง|เส้นทางสำรองมาก แต่ใช้ลิงก์ n(n−1)/2 เส้น|

Full mesh 5 โหนดใช้ 5×4/2 = **10 ลิงก์** หาร 2 เพราะลิงก์ A–B กับ B–A นับเป็นลิงก์คู่เดียวตามโจทย์ลิงก์สองทิศทาง อย่าสับสน **physical topology** การต่อจริง กับ **logical topology** เส้นทางหรือการใช้สื่อเชิงตรรกะ

**จุดหลอก:** ไม่ดู mask; ใช้ network/broadcast เป็น host; AD ชนะ prefix ยาวกว่า; ตั้งเฉพาะ route ขาไป; คิดว่าทุก switch port คือ subnet ใหม่

## 4. Link Layer และ LAN: frame เดินทางในวงอย่างไร

### 4.1 Link Layer รับช่วงไหนของงาน

ถ้า Network สนใจว่าจะพา packet ไปเครือข่ายปลายทางอย่างไร Link Layer สนใจว่าบนลิงก์นี้จะส่งข้อมูลถึงอีกฝั่งด้วยกติกาอะไร เช่น วางขอบเขต frame ใช้ address แบบไหน ตรวจความผิดพลาดอย่างไร และหลายอุปกรณ์จะแชร์สื่อกันอย่างไร

บริการขึ้นกับเทคโนโลยี ไม่ใช่ทุก Link Layer มี reliability แบบเดียวกัน Ethernet ตรวจ FCS แล้วทิ้ง frame ที่ผิดโดยทั่วไป แต่ไม่ได้มี ACK/ส่งซ้ำข้อมูลปกติแบบเดียวกับ Wi-Fi unicast การที่ TCP ส่งซ้ำปลายทางได้ก็เป็นอีกชั้นหนึ่ง

### 4.2 Ethernet Frame มีอะไรบ้าง

มองโครงสร้างหลักเป็น **Destination MAC → Source MAC → Type/Length → Payload → FCS** โดยมีรายละเอียดการส่งบนสื่อเพิ่มเติม เช่น preamble/SFD และ inter-frame gap ที่ต้องแยกจากการนับขนาด frame ในบางโจทย์

Destination บอกให้ใคร Source บอกมาจากใคร Type ช่วยบอก protocol ข้างใน เช่น IPv4 ส่วน **FCS — Frame Check Sequence** ใช้ค่าตรวจ CRC เพื่อช่วยตรวจความผิดพลาด ไม่ใช่รหัสลับหรือกลไกยืนยันว่าผู้ส่งเป็นคนดี

MAC แบบ Ethernet ทั่วไปมี 48 บิต เช่น `00:11:22:33:44:55` มี 6 octets แสดงด้วยเลขฐานสิบหก อย่าสับสนกับ IPv4 32 บิตหรือ IPv6 128 บิต

### 4.3 Switch เรียนรู้จาก source แต่ส่งโดยดู destination

สมมติ A ต่อ port 1, B ต่อ port 2 และ MAC table ยังว่าง เมื่อ A ส่ง frame มาหา B Switch จะจำก่อนว่า “MAC ของ A อยู่ทาง port 1” โดยดู **source MAC กับพอร์ตรับ** จากนั้นค้น **destination MAC ของ B** หากยังไม่รู้ จะส่งสำเนาไปพอร์ตอื่นภายใน VLAN เดียวกัน ยกเว้นพอร์ตรับ เรียก unknown-unicast flooding

เมื่อ B ตอบกลับ Switch เรียนรู้ MAC ของ B ทาง port 2 ตอนนี้รู้ A แล้ว จึงส่งกลับเฉพาะ port 1 การเรียนรู้ไม่ต้องให้ผู้ดูแลกรอก MAC ทุกเครื่องด้วยตนเองตามปกติ และรายการอาจหมดอายุเมื่อไม่ได้ใช้งาน

|กรณีที่ switch พบ|พฤติกรรมทั่วไปใน VLAN|
|Known unicast ปลายทางอยู่อีกพอร์ต|ส่งไปพอร์ตที่เรียนรู้|
|Known unicast ปลายทางอยู่พอร์ตเดียวกับที่รับ|ไม่ส่งย้อนกลับพอร์ตนั้น|
|Unknown unicast|Flood ยกเว้นพอร์ตรับ|
|Broadcast|Flood ตามขอบเขต VLAN ยกเว้นพอร์ตรับ|

Broadcast MAC คือ **FF:FF:FF:FF:FF:FF** อย่าเอาไปปนกับ IPv4 limited broadcast 255.255.255.255 ซึ่งอยู่คนละชั้น

### 4.4 Collision Domain ต่างจาก Broadcast Domain

**Collision domain** คือขอบเขตที่การส่งบนสื่อร่วมอาจชนกันได้ Hub แบบเก่าทำให้เครื่องหลายพอร์ตแชร์สื่อและ collision domain ส่วน switch แยกเป็นลิงก์ตามพอร์ต และเมื่อเป็น switched full-duplex จะไม่มีการชนแบบ shared half-duplex ตามการทำงานปกติ

**Broadcast domain** คือขอบเขตที่ broadcast ชั้น 2 ถูกกระจายไปถึง Switch ที่ยังอยู่ VLAN เดียวกันไม่ได้แยก broadcast domain ให้ทุกพอร์ต ส่วน **แต่ละ VLAN เป็นคนละ broadcast domain** และ router ไม่ส่งต่อ broadcast ชั้น 2 แบบปกติข้าม interface

ตัวอย่าง switch 8 พอร์ต ใช้ 4 พอร์ตใน VLAN 10 และ 4 พอร์ตใน VLAN 20 มี broadcast domains ตาม VLAN **2 วง** ภายใต้การตั้งค่านี้ อย่าตอบ 8 โดยเอาจำนวนพอร์ตมาแทน

### 4.5 CSMA/CD กับ CSMA/CA จำจากเหตุผล

Ethernet แบบเก่าที่ใช้สื่อร่วมและ half-duplex ต้องรับมือหลายเครื่องส่งพร้อมกัน จึงใช้ **CSMA/CD — Carrier Sense Multiple Access with Collision Detection** ฟังสื่อก่อนส่ง ตรวจ collision แล้วรอแบบ backoff เพื่อส่งใหม่ แต่ **Ethernet full-duplex ไม่ต้องใช้ CSMA/CD** ในการทำงานปกติ

Wi-Fi ใช้ **CSMA/CA — Collision Avoidance** เพราะเครื่องไร้สายไม่สามารถพึ่งการฟังขณะส่งเพื่อรู้ collision แบบสื่อสายร่วมได้เหมือนกัน จึงมีกลไกลดโอกาสชน เช่น ฟังช่อง สุ่ม backoff และ ACK ตามชนิด frame คำว่า avoid ไม่ได้แปลว่าจะไม่มี collision เลย

### 4.6 CRC, Parity และการส่งซ้ำเป็นคนละกลไก

Parity แบบหนึ่งบิตช่วยตรวจความผิดพลาดบางรูปแบบ แต่เมื่อพลิกบิตเป็นจำนวนคู่ parity อาจยังเหมือนเดิม **CRC** มองชุดบิตเป็น polynomial และหาค่าเศษตาม generator ที่กำหนด ผู้รับตรวจความสอดคล้องจากค่าที่ส่งมา ความสามารถตรวจขึ้นกับ generator และรูปแบบ error จึงไม่ควรตอบว่า CRC ตรวจทุกกรณีได้ 100%

**Error detection** คือรู้ว่ามีความผิดปกติตามความสามารถของรหัส **Error correction** คือกู้ข้อมูลจากความซ้ำซ้อนที่ออกแบบมา **Retransmission** คือขอหรือจัดให้ส่งซ้ำเมื่อผิด/หาย สามอย่างนี้ไม่ใช่คำเดียวกัน

ใน Stop-and-Wait ผู้ส่งส่งหนึ่งหน่วยแล้วรอ ACK หาก ACK หายอาจส่งข้อมูลเดิมซ้ำ จึงต้องมี sequence number ช่วยแยกว่าเป็นข้อมูลใหม่หรือ duplicate ถ้าเพิ่ม pipeline จะส่งหลายหน่วยค้างได้ แต่ต้องออกแบบ window และพื้นที่ sequence ให้เหมาะสม

### 4.7 VLAN, Trunk และ STP

VLAN แบ่งวงเชิงตรรกะแม้ใช้ switch ตัวเดียวกัน Port แบบ access มักรับส่งของ VLAN ที่กำหนดสำหรับเครื่องปลายทาง ส่วน **trunk** ขนส่งได้หลาย VLAN บนลิงก์เดียว โดย **802.1Q tag** ช่วยระบุ VLAN ตามกติกาและการตั้งค่า เช่น traffic ของ native VLAN อาจไม่ติด tag ในบางบริบท

เครื่องคนละ VLAN จะคุย IP กันต้องมี **Inter-VLAN routing** ผ่าน router หรือ layer-3 switch ไม่ใช่แค่ลาก trunk แล้วทุก VLAN จะคุยกันเอง

การต่อ switch หลายเส้นเป็นวงทำให้มีเส้นทางสำรอง แต่ถ้าปล่อย loop ชั้น 2 อาจเกิด broadcast storm และ MAC table สลับไปมา **STP — Spanning Tree Protocol** ช่วยเลือก topology ที่ไม่วน โดยบล็อกบางเส้นทางไว้ตามกระบวนการ ไม่ได้แปลว่าต้องถอดสายสำรองทิ้ง

**จุดหลอก:** switch เรียนรู้จาก source ไม่ใช่ destination; unknown unicast ไม่ได้ flood ข้ามทุก VLAN; VLAN ต้อง route เพื่อข้ามวง; CRC ไม่แก้ทุกบิต; full-duplex Ethernet ไม่ใช้ CD ตามปกติ

## 5. LAN Cabling: ไม่ใช่แค่จำสีสาย

### 5.1 ทำไมต้องเป็นคู่บิดเกลียว

คู่สายส่งสัญญาณแบบ differential โดยพิจารณาความต่างระหว่างตัวนำ การบิดเกลียวทำให้สภาพการรับรบกวนของสองเส้นใกล้เคียงกันและช่วยลด crosstalk ระหว่างคู่ จึงสำคัญว่าเส้นไหนเป็นคู่กับเส้นไหน ไม่ใช่มีทองแดงครบแปดเส้นแล้วถือว่าใช้แทนกันได้

**UTP** ไม่มีชิลด์ ส่วน **STP** มีโครงสร้างชิลด์ตามชนิดสาย ชิลด์ต้องติดตั้งและต่อกราวด์ตามระบบอย่างถูกต้อง จึงไม่ควรสรุปว่าเอาสายมีชิลด์มาเสียบแบบใดก็ชนะ UTP ทุกกรณี สาย Ethernet twisted pair ทั่วไปมี **4 คู่ รวม 8 เส้น** และหัว 8P8C ที่มักเรียก RJ-45

### 5.2 T568A กับ T568B: จดตารางให้เห็น pin

ลำดับนี้เป็นเลข pin 1–8 ตามมาตรฐาน **ต้องดูทิศหัวและทิศหน้าสัมผัสให้ถูกก่อนนับ** การพลิกหัวแล้วอ่านซ้ายไปขวาอาจได้ลำดับกลับกัน แม้ท่องสีถูก

|Pin|T568A|T568B|
|---|---|---|
|1|ขาวเขียว|ขาวส้ม|
|2|เขียว|ส้ม|
|3|ขาวส้ม|ขาวเขียว|
|4|น้ำเงิน|น้ำเงิน|
|5|ขาวน้ำเงิน|ขาวน้ำเงิน|
|6|ส้ม|เขียว|
|7|ขาวน้ำตาล|ขาวน้ำตาล|
|8|น้ำตาล|น้ำตาล|

วิธีจำคือ A กับ B สลับ **คู่เขียวกับคู่ส้ม** ส่วนคู่สีน้ำเงินและน้ำตาลอยู่ที่เดิม สังเกตว่าคู่หนึ่งอาจไม่ได้อยู่ pin ติดกัน เช่นคู่ที่ใช้ pin 3 และ 6 จึงต้องรักษาการเข้าคู่ตามมาตรฐาน

### 5.3 สายตรง สายไขว้ และ Auto MDI-X

**Straight-through** ใช้มาตรฐานเดียวกันสองปลาย เช่น B–B หรือ A–A ส่วน **crossover แบบที่สอนกับ 10/100BASE-TX** ใช้ A–B เพื่อไขว้คู่ส่ง/รับตามบริบทนั้น คำว่าคนละมาตรฐานสองปลายไม่ได้หมายความว่าเสียทุกกรณี ต้องดูว่าเจตนาทำสายแบบไหน

ตามกฎเดิมเมื่อไม่มี Auto MDI-X: PC–switch ใช้สายตรง ส่วน switch–switch แบบ 10/100 ใช้สายไขว้ อุปกรณ์ที่รองรับ **Auto MDI-X** สามารถจัดการคู่ส่ง/รับให้อัตโนมัติ จึงอย่าใช้กฎเก่าไปตอบแบบเหมารวมกับอุปกรณ์ทุกรุ่น

สาย **rollover/console** ใช้บริบทการเข้าจัดการอุปกรณ์ ไม่ใช่เอาไปแทนสาย Ethernet ปกติได้เพราะหัวหน้าตาคล้ายกัน และ 1000BASE-T ใช้ครบ **4 คู่** จึงไม่ควรยกแผนผังคู่ส่ง/รับของ 100BASE-TX ไปอธิบายทุกเทคโนโลยี

### 5.4 Category, ระยะ และความเร็ว

|ตัวอย่างสาย/ลิงก์|จำอะไร|เงื่อนไขที่ห้ามลืม|
|Cat5e กับ 1000BASE-T|รองรับ 1 Gb/s ที่ channel ได้มาตรฐานถึง 100 m|หัวต่อ การติดตั้งและอุปกรณ์ต้องรองรับด้วย|
|Cat6A กับ 10GBASE-T|รองรับ 10 Gb/s ที่ 100 m ตามมาตรฐาน channel|Transceiver/port บางรุ่นอาจมีข้อจำกัดเฉพาะ|
|Cat6 กับ 10GBASE-T|ระยะและ crosstalk เป็นเงื่อนไขสำคัญ|อย่าเหมารวมว่าได้ 100 m ทุกการติดตั้ง|
|Fiber optic|ใช้แสงและทน EMI ในตัวกลาง|ชนิด fiber ความยาวคลื่น และ transceiver ต้องเข้ากัน|

Channel ทองแดง LAN แบบทั่วไปยาวรวม **100 m** โดยส่วน **permanent link มัก 90 m** และเผื่อ patch cords รวม 10 m นี่ไม่ใช่ค่าระยะของ Ethernet ทุกชนิด เพราะ fiber และมาตรฐานอื่นมีข้อกำหนดต่างกัน

ความเร็วใช้งานจริงต้องพอดีกันทั้งสาย หัวต่อ NIC, switch port, การเจรจาความเร็ว และเส้นทางอื่น การเปลี่ยนสายเป็น Cat6A อย่างเดียวไม่ได้ทำให้พอร์ต 1 Gb/s กลายเป็น 10 Gb/s

### 5.5 Fiber ต่างจากทองแดงอย่างไร

Fiber ใช้แสง ไม่รับ EMI ในตัวกลางเหมือนสายไฟฟ้า และเหมาะกับหลายงานระยะไกล **Single-mode** ใช้การส่งโหมดหลักตามโครงสร้าง เหมาะกับระยะไกลในหลายระบบ ส่วน **multimode** รองรับหลายโหมดแสงและมีข้อจำกัด modal dispersion ระยะจริงขึ้นกับมาตรฐาน อัตราส่ง ชนิด fiber และ optics

ต้องเลือกหัวต่อ/สาย/โมดูลให้ตรง ไม่ใช่เห็นว่าเป็น fiber เหมือนกันแล้วต่อได้เสมอ อีกทั้งแสงในใยแก้วไม่ทำให้ latency เป็นศูนย์ เพราะยังมี propagation และเวลาประมวลผล

### 5.6 อาการสายเสียที่ข้อสอบชอบถาม

- **Open:** ตัวนำขาดหรือหน้าสัมผัสไม่ถึงกัน
- **Short:** ตัวนำที่ไม่ควรแตะกันกลับลัดวงจร
- **Miswire:** ต่อ pin ผิดตำแหน่ง
- **Split pair:** pin อาจต่อถึงกัน แต่หยิบตัวนำคนละคู่มาจับคู่ ทำให้คุณภาพสัญญาณผิด

เครื่องทดสอบ continuity แบบง่ายอาจบอกเพียงว่า pin ต่อถึงกัน ไม่ได้ยืนยันประสิทธิภาพทุกความถี่หรือการจับคู่ถูกทั้งหมด การตรวจคุณภาพตามมาตรฐานต้องใช้เครื่องมือที่วัดได้เหมาะกับงาน

**PoE — Power over Ethernet** ส่งไฟร่วมกับข้อมูลให้อุปกรณ์ที่รองรับ เช่น AP และ IP phone แต่ต้องดูมาตรฐาน กำลังไฟและ power budget ของสวิตช์ด้วย ไม่ใช่มีสาย LAN แล้วจ่ายไฟให้อุปกรณ์ทุกชนิดได้

**จุดหลอก:** หัวถูกสีแต่ split pair ยังมีปัญหา; Link LED ไม่รับรอง IP/DNS; สายใหม่ไม่เพิ่มความเร็วพอร์ตเกินที่รองรับ; 100 m เป็นเงื่อนไขของ channel ที่กำลังพูดถึง

## 6. Cloud Computing: เช่าความสามารถแบบไหน ใครต้องดูแลอะไร

### 6.1 Cloud ไม่ใช่แค่ “ฝากไฟล์ไว้บน Internet”

Cloud คือรูปแบบบริการที่ผู้ใช้ขอและใช้งานทรัพยากรคอมพิวเตอร์ผ่านเครือข่ายได้สะดวก ผู้ให้บริการมีทรัพยากรรวมและจัดสรรตามความต้องการ ทรัพยากรอาจเป็นเครื่องเสมือน storage, database, platform หรือแอปสำเร็จรูป ไม่ได้จำกัดแค่พื้นที่ฝากไฟล์

นึกถึงการใช้ไฟฟ้า เราต้องการกำลังไฟ ไม่จำเป็นต้องสร้างโรงไฟฟ้าทุกครั้ง แต่การเปรียบเทียบนี้ไม่ได้หมายความว่า cloud ใช้งานแล้วคิดเงินรูปแบบเดียวทุกเจ้า หรือไม่ต้องดูแลอะไรเลย ต้องอ่านขอบเขตบริการและสัญญา

### 6.2 คุณลักษณะหลัก 5 อย่างของ NIST

**On-demand self-service:** ผู้ใช้จัดสรรทรัพยากรได้เองตามบริการ เช่นสร้าง VM ผ่านหน้าเว็บหรือ API โดยไม่ต้องให้เจ้าหน้าที่ทำทุกครั้ง คำว่า self-service ไม่ได้แปลว่าไม่ต้องมีสิทธิ์หรือไม่ต้องผ่านนโยบายองค์กร

**Broad network access:** เข้าถึงผ่านเครือข่ายด้วยกลไกมาตรฐาน จาก client ที่รองรับ ไม่ได้แปลว่าทุกทรัพยากรต้องเปิด public Internet เสมอ Private cloud ก็เข้าถึงผ่านเครือข่ายได้

**Resource pooling:** ผู้ให้บริการรวมทรัพยากรไว้เป็น pool แล้วจัดสรรให้หลายผู้ใช้หรือผู้เช่า โดยมีการแยกตามการออกแบบ ไม่ใช่ทุกคนแชร์บัญชีเดียวกันหรือมองเห็นข้อมูลกันได้

**Rapid elasticity:** เพิ่มและลดทรัพยากรได้รวดเร็วตามความต้องการ เช่นเพิ่มจำนวนเครื่องช่วงลงทะเบียน แล้วลดเมื่อหมดช่วงงาน ความสามารถนี้ต้องมีการออกแบบและขอบเขตบริการรองรับ

**Measured service:** ระบบวัดและรายงานปริมาณการใช้ เช่นเวลาประมวลผล พื้นที่หรือ bandwidth ช่วยให้ติดตามและควบคุมได้ ไม่ได้กำหนดว่าต้องคิดเงินนาทีละเท่าไร หรือถูกกว่าเสมอ

จำสั้น ๆ ว่า **ขอเอง — เข้าผ่านเครือข่าย — ใช้ pool — ยืดหด — วัดการใช้** การมี VM เพียงตัวเดียวในห้อง server ยังพิสูจน์คุณลักษณะเหล่านี้ไม่ครบ

### 6.3 IaaS, PaaS และ SaaS: ต่างกันที่ส่วนที่บริการจัดให้

**IaaS — Infrastructure as a Service:** ได้พื้นฐานอย่าง VM, network และ storage ผู้ให้บริการดูแลโครงสร้างพื้นฐานตามข้อตกลง ส่วนลูกค้ามักดูแล guest OS, patches ฝั่งตน แอปและข้อมูล เหมาะเมื่ออยากควบคุมเครื่องมาก แต่ต้องมีความสามารถดูแลระบบ

**PaaS — Platform as a Service:** ผู้ให้บริการดูแล platform/runtime ตามขอบเขตที่เสนอ ลูกค้าเน้น deploy โค้ด จัดข้อมูลและตั้งค่าของแอป ลดภาระดูแล OS แต่มีข้อจำกัดด้านภาษา runtime และวิธี deploy ที่ต้องยอมรับ

**SaaS — Software as a Service:** ใช้แอปสำเร็จรูปเป็นบริการ เช่นแอปเอกสารออนไลน์ในบริบทที่ให้เป็นบริการ ผู้ใช้ไม่ต้องดูแล OS ของระบบแอปนั้น แต่ยังต้องจัดสิทธิ์บัญชี ตั้งค่าการแชร์ และจัดการข้อมูลตามหน้าที่ของตน

|สิ่งที่ถาม|IaaS โดยทั่วไป|PaaS โดยทั่วไป|SaaS โดยทั่วไป|
|---|---|---|---|
|ลูกค้าได้อะไร|โครงสร้างพื้นฐานเสมือน|สภาพแวดล้อมรันแอป|แอปพร้อมใช้|
|Guest OS ของบริการนั้น|ลูกค้าดูแล|ผู้ให้บริการดูแลตามขอบเขต|ผู้ให้บริการดูแล|
|โค้ดของแอปลูกค้า|ลูกค้าจัดการ|ลูกค้าจัดการ|ผู้ให้บริการจัดแอปหลักให้|
|สิทธิ์บัญชีและข้อมูลฝั่งผู้ใช้|ยังมีหน้าที่|ยังมีหน้าที่|ยังมีหน้าที่|

ขอบเขตจริงอาจต่างตามบริการ จึงควรตอบจาก **สิ่งที่ลูกค้าต้องจัดการในโจทย์** ไม่ใช่จำแค่ชื่อแบรนด์ว่าแบรนด์นี้เป็น IaaS เท่านั้น

### 6.4 Public, Private, Community และ Hybrid

**Public cloud** เปิดให้สาธารณะสมัครใช้ตามบริการ ส่วน **private cloud** จัดไว้ให้ใช้งานเฉพาะองค์กรหนึ่ง Private ไม่ได้บังคับว่าต้องอยู่ในตึกบริษัทหรือดูแลเองทั้งหมด และ public ไม่ได้แปลว่าใครก็อ่านข้อมูลของลูกค้าได้

**Community cloud** ใช้ร่วมโดยกลุ่มองค์กรที่มีข้อกำหนดหรือความต้องการร่วมกัน ส่วน **hybrid cloud** เป็นการประกอบ cloud ที่ยังแยกกันตั้งแต่สองโครงสร้าง โดยเชื่อมด้วยเทคโนโลยีที่รองรับการใช้งานหรือการเคลื่อนย้ายข้อมูล/แอปตามการออกแบบ การมี server เก่าเชื่อม Internet เพียงอย่างเดียวไม่พอให้สรุปว่าเป็น hybrid cloud ตามนิยามครบ

**Multi-cloud** หมายถึงการใช้ cloud หลายผู้ให้บริการตามบริบท ไม่จำเป็นต้องเท่ากับ hybrid ทุกกรณี และไม่ได้อยู่ในชุด deployment models หลัก 4 แบบของนิยาม NIST ที่ใช้ทวนนี้

### 6.5 Scalability, Elasticity และ Load Balancer

**Scalability** คือความสามารถรองรับงานที่มากขึ้นด้วยการปรับทรัพยากร **Scale up / vertical scaling** เพิ่มความสามารถเครื่องเดิม เช่น CPU/RAM ส่วน **scale out / horizontal scaling** เพิ่มจำนวนเครื่อง

**Elasticity** เน้นปรับให้เข้ากับความต้องการที่ขึ้นลง ไม่ใช่ขยายอย่างเดียว **Load balancer** กระจายคำขอไป backend ส่วน **auto scaling** ปรับทรัพยากรตามนโยบาย ทั้งสองเกี่ยวข้องกัน แต่ไม่ได้ทำหน้าที่แทนกัน

ตัวอย่างร้านออนไลน์มี 2 instances ปกติ ช่วงโปรโมชันเพิ่มเป็น 8 แล้วลดเหลือ 2 เมื่อจบ เป็นภาพของ elasticity ส่วนแอปจะ scale out ได้ดีต้องจัดการ session, shared data, database และคอขวดด้วย การเพิ่มเว็บเซิร์ฟเวอร์ไม่ช่วยเต็มที่ถ้า database เป็นคอขวดอยู่

### 6.6 VM, Container และ Serverless อย่าเอามาปนกัน

**VM** จำลองเครื่องให้มี guest OS ของตนเองบน virtualization layer ส่วน **container** โดยทั่วไปแยกแอปและ dependencies โดยแชร์ kernel ของ host ตามสถาปัตยกรรม จึงต่างกันที่ชั้นการแยกและรูปแบบจัดการ ไม่ใช่ container เป็น VM ที่แค่เปลี่ยนชื่อ

**Serverless** หมายถึงผู้ใช้ไม่ต้องจัดการ server ในแบบเดิมสำหรับบริการนั้น เช่นส่งฟังก์ชันให้ระบบรันตาม event ยังมี server จริงอยู่เบื้องหลัง และลูกค้ายังต้องดูแลโค้ด สิทธิ์ ข้อมูลและการตั้งค่า ไม่ใช่ทำอะไรก็ฟรีหรือขยายได้ไม่จำกัด

### 6.7 Storage, Backup, Availability และ Disaster Recovery

**Object storage** เก็บเป็น object พร้อม identifier/metadata และเข้าถึงผ่าน API ตามบริการ **Block storage** ให้ block ที่ประกอบเป็น volume สำหรับระบบ **File storage** ให้การเข้าถึงไฟล์ผ่าน interface/protocol ของบริการ เลือกให้ตรงวิธีใช้งาน ไม่ใช่ storage ทุกแบบแทนกันโดยไม่มีผล

**Replication** ทำสำเนาข้อมูลเพื่อวัตถุประสงค์เช่นความพร้อมใช้ แต่หากลบไฟล์ผิด ระบบอาจ replicate การลบด้วย **Backup** เน้นสำเนาสำหรับกู้คืนตามนโยบาย ต้องมี retention, การป้องกันสำเนา และทดสอบ restore ไม่ใช่มีคำว่า backup ในหน้าจอแล้วรับรองกู้ได้

**RPO — Recovery Point Objective:** ยอมสูญข้อมูลย้อนหลังได้กี่นาที/ชั่วโมง **RTO — Recovery Time Objective:** ตั้งเป้าให้กู้บริการกลับภายในเวลาเท่าไร ถ้าสำรองทุก 24 ชั่วโมงแบบไม่มีวิธีเก็บเพิ่ม ก็ไม่ควรอ้างว่ารองรับ RPO 5 นาทีได้โดยอัตโนมัติ

**SLA** ระบุระดับบริการ วิธีวัด เงื่อนไข ข้อยกเว้นและการชดเชย ไม่ได้รับประกันว่าไม่มี downtime ทุกกรณี หากใช้แบบจำลองเดือน 30 วัน SLA 99.9% จะมีช่วงไม่พร้อมใช้ตามสัดส่วน 0.1%×30×24×60 = **43.2 นาที** แต่การนับจริงต้องอิงสัญญา ไม่ใช่เอาตัวเลขนี้ไปแทนทุก SLA

### 6.8 ต้นทุนและ Shared Responsibility

**Shared responsibility** หมายถึงผู้ให้บริการกับลูกค้ามีหน้าที่ต่างส่วนตามบริการ เช่น IaaS ลูกค้ามักต้อง patch guest OS แต่ SaaS ไม่ได้ให้ลูกค้าเข้าไป patch OS ของระบบแอปเอง อย่างไรก็ดี การกำหนดสิทธิ์บัญชีและการแชร์ข้อมูลฝั่งลูกค้ายังสำคัญ

ใช้ **least privilege** ให้สิทธิ์เท่าที่จำเป็น ใช้ MFA ตามการรองรับ แยกข้อมูลลับและจัดการ key ให้เหมาะสม การเข้ารหัสไม่ได้ช่วยถ้าตั้งสิทธิ์ให้ผู้ไม่เกี่ยวข้องอ่านข้อมูลโดยตรงได้

ค่าใช้จ่ายอาจเกิดจาก compute, storage, snapshot, API requests และ data egress ตามรูปแบบราคา ทรัพยากรที่เปิดทิ้งอาจคิดเงินแม้ไม่มีคนใช้เว็บ และ budget alert โดยทั่วไปเป็นการเตือน ไม่ใช่กลไกหยุดค่าใช้จ่ายทุกประเภทโดยอัตโนมัติ ต้องออกแบบมาตรการคุมให้ตรงบริการ

**จุดหลอก:** cloud ไม่ใช่ VM ทุกตัว; public ไม่ได้แปลว่าข้อมูลเปิดสาธารณะ; SaaS ไม่ได้ลบหน้าที่ผู้ใช้ทั้งหมด; replication ไม่แทน backup; serverless ยังมี server; measured service ไม่ได้แปลว่าถูกกว่าเสมอ

## 7. Wireless: เชื่อมชื่อ Wi-Fi ได้ ทำไมยังใช้ Internet ไม่ได้

### 7.1 แยก AP ออกจาก Wireless Router ก่อน

**Access Point — AP** เชื่อม client ไร้สายเข้าระบบลิงก์ ไม่จำเป็นต้องเป็น router หรือ DHCP server ส่วน **wireless router บ้าน** มักรวม AP, Ethernet switch, IP router, DHCP และ NAT ในกล่องเดียว เวลาโจทย์บอกว่า “ตั้งค่า wireless router” ต้องดูว่ากำลังตั้งหน้าที่ใด

**SSID** คือชื่อ WLAN ที่เห็นตอนเลือกเครือข่าย ส่วน **BSSID** ระบุ Basic Service Set โดยทั่วไปสัมพันธ์กับ MAC ของ AP radio ตามการใช้งาน ระบบหลาย AP อาจใช้ SSID เดียวกันได้ ชื่อเหมือนกันไม่ได้แปลว่าเชื่อมวิทยุตัวเดียวกัน

**Infrastructure mode** ให้ client ติดต่อผ่าน AP ส่วน **ad hoc** ตามแนวคิด WLAN ให้สถานีสื่อสารโดยไม่ใช้ AP ในโหมดนั้น การสื่อสารแบบ mesh เป็นอีกบริบทที่ต้องดู protocol และการออกแบบ ไม่ใช่เห็นไม่มีสายแล้วเรียก ad hoc ทั้งหมด

### 7.2 Wi-Fi ต้องแชร์ airtime

Wi-Fi อยู่ในตระกูล **IEEE 802.11** ใช้สื่อวิทยุที่หลายสถานีแบ่งเวลากัน สถานีต้องฟังช่อง รอและสุ่ม backoff ตามกลไก CSMA/CA การส่งข้อมูลยังมี overhead, ACK ตามชนิด frame และการส่งซ้ำเมื่อจำเป็น

ดังนั้นตัวเลข PHY rate ที่เห็น เช่นอัตราเชื่อมต่อที่อุปกรณ์รายงาน ไม่เท่ากับ throughput แอปที่รับประกัน เมื่อมี client มากขึ้น ทุกคนอาจแย่ง airtime ร่วมกัน ไม่ใช่ทุกเครื่องได้ความเร็วเต็มตามโฆษณาพร้อมกัน

Client ที่อยู่ไกลหรือสภาพสัญญาณไม่ดีอาจใช้อัตราส่งต่ำและมี retransmission ทำให้กิน airtime มากกว่าข้อมูลจำนวนเท่ากันที่ส่งในสภาพดี ผลกระทบจึงไม่ได้ขึ้นกับจำนวนคนอย่างเดียว ต้องดูรูปแบบ traffic และคุณภาพลิงก์ด้วย

### 7.3 Hidden Node และ RTS/CTS

สมมติ A กับ C อยู่คนละมุม ได้ยิน AP แต่ไม่ได้ยินกันเอง A ฟังแล้วคิดว่าว่าง C ก็คิดว่าว่าง จึงส่งพร้อมกันจนชนที่ AP ปัญหานี้คือ **hidden node** ไม่ใช่การซ่อน SSID

**RTS/CTS** ช่วยประกาศการจองสื่อให้สถานีที่ได้ยินทราบช่วงเวลาใช้งาน จึงลดผลปัญหาได้บางกรณี แต่เพิ่ม overhead และไม่ใช่วิธีแก้ทุกปัญหา Wi-Fi การเลือกใช้ต้องดูขนาด frame และสภาพแวดล้อม

### 7.4 2.4 GHz, 5 GHz และการวาง Channel

2.4 GHz มักมีลักษณะครอบคลุมและผ่านสิ่งกีดขวางได้ดีกว่า 5 GHz เมื่อเทียบภายใต้เงื่อนไขที่เหมาะสม แต่ย่านนี้มักแออัด ส่วน 5 GHz มีตัวเลือกช่องให้วางแผนมากกว่าในหลายบริบท ระยะจริงยังขึ้นกับกำลังส่ง เสาอากาศ วัสดุกำแพงและ noise จึงไม่ควรใช้ความถี่อย่างเดียวฟันธงระยะ

สำหรับ 2.4 GHz แบบ channel width 20 MHz นิยมวาง **channel 1, 6, 11** เพื่อลดการทับซ้อนของช่องใกล้กัน การวาง AP ใกล้กันที่ช่อง 1 กับ 2 ไม่ได้แปลว่าแยกกันดีเพราะเลขต่างกัน ส่วนช่องและกำลังส่งที่ใช้ได้ต้องตรงกฎของประเทศและอุปกรณ์

เพิ่ม channel width อาจเพิ่มอัตราส่งสูงสุด แต่กินสเปกตรัมมากขึ้นและอาจเพิ่มปัญหาการรบกวน จึงไม่ใช่กว้างที่สุดแล้วดีที่สุดเสมอ ในห้องที่มี AP หนาแน่น การจัดช่องและกำลังส่งอย่างมีข้อมูลอาจสำคัญกว่าการตั้งแรงสุดทุกตัว

### 7.5 RSSI, dBm และ SNR อ่านอย่างไร

**RSSI** สื่อถึงระดับสัญญาณรับตามวิธีรายงานของอุปกรณ์ หากเปรียบเทียบกำลังรับแบบ dBm ในบริบทเดียวกัน **−50 dBm แรงกว่า −80 dBm** เพราะติดลบน้อยกว่า อย่าดูเพียงตัวเลข 80 มากกว่า 50 แล้วสรุปผิด

**SNR — Signal-to-Noise Ratio** เปรียบเทียบสัญญาณกับ noise ในหน่วย dB สามารถหาผลต่างจากกำลัง dBm ได้ ตัวอย่างสัญญาณ −60 dBm และ noise −90 dBm → SNR = **30 dB** ไม่ใช่ −150 dB SNR ที่ดีช่วยให้แยกสัญญาณและรองรับ modulation ที่เหมาะสมขึ้น แต่ throughput ยังขึ้นกับปัจจัยอื่น

สัญญาณแรงไม่ได้ยืนยันว่าเร็วเสมอ ถ้าช่องแออัด Internet backhaul ช้า หรือ server ปลายทางช้า ก็ยังใช้งานช้าได้

### 7.6 ความปลอดภัย: รหัสแต่ละชนิดไม่เหมือนกัน

**WEP** และ **WPA/TKIP** เป็นกลไกเก่าที่ควรหลีกเลี่ยง ใช้รูปแบบเช่น WPA2-AES/CCMP หรือ WPA3 ตามการรองรับและข้อกำหนดของระบบ **Personal** มักใช้รหัสร่วมตามโหมด ส่วน **Enterprise** มักใช้ 802.1X/EAP ร่วมระบบยืนยันตัวตน เช่น RADIUS ตามสถาปัตยกรรม

อย่าสับสน **รหัสเข้า Wi-Fi** กับ **รหัส admin ของ router** รหัสแรกให้ client เชื่อม WLAN ส่วนรหัสหลังให้แก้การตั้งค่าอุปกรณ์ การเปลี่ยนอันเดียวไม่ได้เปลี่ยนอีกอันโดยอัตโนมัติ

ซ่อน SSID ไม่ใช่การเข้ารหัส และ MAC filtering ไม่แทนระบบยืนยันตัวตนที่เหมาะสม เพราะ MAC อาจถูกปลอมได้ ส่วนเว็บที่ใช้ HTTPS ปกป้อง traffic แอประดับหนึ่งก็ยังไม่แทนการดูแล WLAN ทั้งระบบ

### 7.7 Roaming และการตรวจปัญหาเป็นลำดับ

**Roaming** คือการย้ายการเชื่อมต่อระหว่าง AP ตามการตัดสินใจของ client และความสามารถระบบ การตั้ง SSID เหมือนกันเฉย ๆ ไม่ได้ยืนยันว่าโทรศัพท์หรือวิดีโอจะต่อเนื่องไม่มีสะดุด ต้องดู coverage, authentication และบริการเครือข่ายประกอบ

เมื่อเชื่อมแล้ว Internet ไม่ได้ ให้ไล่เป็นขั้น:

1. NIC/radio เปิดหรือไม่ และ client เห็น SSID ที่ถูกหรือไม่
2. Security mode/key ตรงกันหรือไม่ และ association สำเร็จหรือไม่
3. ได้ IP, mask, gateway และ DNS ที่ถูกหรือไม่
4. ติดต่อ gateway ได้หรือไม่ โดยคำนึงว่า ICMP อาจถูกจำกัด
5. Routing, NAT และ WAN ของ router ใช้งานหรือไม่
6. DNS resolve ชื่อได้หรือไม่ และบริการเว็บปลายทางพร้อมหรือไม่

**จุดหลอก:** เห็น SSID ไม่เท่ากับผ่าน authentication; ผ่าน authentication ไม่เท่ากับได้ DHCP; ได้ DHCP ไม่เท่ากับออก Internet; ซ่อนชื่อไม่ใช่เข้ารหัส; throughput ไม่เท่ากับ PHY rate

## 8. Cisco และ Packet Tracer: เข้าใจคำสั่งผ่านเครือข่ายตัวอย่าง

### 8.1 อ่าน Prompt ก่อนพิมพ์

IOS แบ่งโหมดเพื่อแยกคำสั่งตรวจสอบและตั้งค่า คำสั่งถูกแต่พิมพ์ผิดโหมดก็ใช้งานไม่ได้ เช่น `ip address` สำหรับ interface ไม่ได้พิมพ์ที่ user EXEC แล้วจะตั้งค่าได้เอง

|Prompt ตัวอย่าง|โหมด|ใช้ทำอะไร|
|---|---|---|
|R1>|User EXEC|คำสั่งใช้งาน/ตรวจสอบพื้นฐานตามสิทธิ์|
|R1#|Privileged EXEC|ตรวจสอบเพิ่มเติม บันทึก และเข้าโหมดตั้งค่า|
|R1(config)#|Global configuration|ตั้งค่าระดับระบบ|
|R1(config-if)#|Interface configuration|ตั้งค่า interface ที่เลือก|

`enable` เข้า privileged EXEC, `configure terminal` เข้า global configuration, `interface ...` เลือก interface, `exit` กลับหนึ่งระดับ ส่วน `end` หรือ Ctrl+Z กลับ privileged EXEC ชื่อ interface และรายละเอียดคำสั่งขึ้นกับรุ่น/ซอฟต์แวร์ ตัวอย่างนี้เป็นแนว Cisco IOS ไม่ใช่คำสั่งสากลของอุปกรณ์ทุกยี่ห้อ

### 8.2 วางแผน IP สำหรับ 2 LAN และ 2 Router

|อุปกรณ์/Interface|IP/Prefix|Gateway ของ host|
|---|---|---|
|PC-A|192.168.1.10/24|192.168.1.1|
|R1 G0/0 ฝั่ง LAN A|192.168.1.1/24|ไม่ตั้งแบบ host ในตารางนี้|
|R1 G0/1 ฝั่ง R2|10.0.0.1/30|ใช้ routing table|
|R2 G0/1 ฝั่ง R1|10.0.0.2/30|ใช้ routing table|
|R2 G0/0 ฝั่ง LAN B|192.168.2.1/24|ใช้ routing table|
|PC-B|192.168.2.10/24|192.168.2.1|

เครือข่าย 10.0.0.0/30 มี usable .1 กับ .2 และ broadcast .3 ใช้เป็นวงเชื่อม router ในตัวอย่าง ส่วน PC สองฝั่งอยู่คนละ /24 อย่าใช้ IP เดียวกันซ้ำระหว่าง interface โดยไม่มีการออกแบบเฉพาะ

### 8.3 ตั้ง R1 แบบทีละขั้น

```text
R1> enable
R1# configure terminal
R1(config)# interface gigabitEthernet0/0
R1(config-if)# ip address 192.168.1.1 255.255.255.0
R1(config-if)# no shutdown
R1(config-if)# exit
R1(config)# interface gigabitEthernet0/1
R1(config-if)# ip address 10.0.0.1 255.255.255.252
R1(config-if)# no shutdown
R1(config-if)# exit
R1(config)# ip route 192.168.2.0 255.255.255.0 10.0.0.2
R1(config)# end
R1# show ip interface brief
R1# show ip route
R1# copy running-config startup-config
```

บรรทัด `ip route` อ่านว่า “ถ้าจะไปเครือข่าย 192.168.2.0/24 ให้ส่งไป next hop 10.0.0.2” **next hop ไม่ใช่ IP ของ PC-B** แต่คือ router ถัดไปที่เข้าถึงได้ R1 รู้ LAN A กับ transit link จากการเชื่อมตรงเมื่อ interface พร้อมใช้งาน จึงเพิ่ม static route สำหรับ LAN B ที่ไม่ได้เชื่อมตรง

ชื่อ interface ในไฟล์กิจกรรมอาจเป็น G0/0/0 หรือชื่ออื่น ต้องใช้ของอุปกรณ์จริง ไม่คัดลอกชื่อ G0/0 ทั้งที่ไม่มีพอร์ตนั้น

### 8.4 ตั้ง R2 และอย่าลืมเส้นทางกลับ

```text
R2> enable
R2# configure terminal
R2(config)# interface gigabitEthernet0/0
R2(config-if)# ip address 192.168.2.1 255.255.255.0
R2(config-if)# no shutdown
R2(config-if)# exit
R2(config)# interface gigabitEthernet0/1
R2(config-if)# ip address 10.0.0.2 255.255.255.252
R2(config-if)# no shutdown
R2(config-if)# exit
R2(config)# ip route 192.168.1.0 255.255.255.0 10.0.0.1
R2(config)# end
R2# copy running-config startup-config
```

ถ้า R1 มี route ไป LAN B แต่ R2 ไม่มี route กลับ LAN A packet ขออาจไปถึง แต่คำตอบกลับไม่ถึงต้นทาง จึงยัง ping ไม่สำเร็จ กรณีนี้แสดงว่าการทดสอบแบบ request/reply ต้องมีเส้นทางทั้งสองทิศ รวมถึงไม่มี ACL/policy บล็อก

ตัวอย่างนี้ไม่ต้องทำ NAT เพื่อให้สอง private LAN คุยกันภายใน topology เพราะ routing ภายในกับการแปลง address เป็นคนละหน้าที่

### 8.5 อ่าน show ip route ให้เข้าใจ

```text
C  10.0.0.0/30 is directly connected, GigabitEthernet0/1
S  192.168.2.0/24 [1/0] via 10.0.0.2
```

`C` คือ connected ส่วน `S` คือ static รูป `[1/0]` ในตัวอย่างอ่านเป็น **[AD/metric]** ไม่ใช่ [hop count/port] และ `via` ระบุ next hop ส่วน `L` ที่อาจเห็นบน IOS คือ local route ของ address interface ตนเอง โดยรายละเอียดรายการขึ้นกับรุ่นและสถานะ

รหัสอื่นที่ควรจำคือ `O` สำหรับ OSPF และ `R` สำหรับ RIP อย่าคิดว่า route ทุกบรรทัดคือ static เพราะมี address เหมือนกัน

### 8.6 คำสั่งตรวจสอบกับ Running/Startup Config

|คำสั่ง|ใช้ตอบคำถามอะไร|
|---|---|
|show ip interface brief|Interface มี IP ใด และ status/protocol เป็นอย่างไร|
|show ip route|มี route ไปเครือข่ายนี้หรือไม่ ใช้ next hop อะไร|
|show running-config|ขณะนี้ตั้งค่าใช้งานไว้อย่างไร|
|show startup-config|มี config อะไรเก็บไว้สำหรับเริ่มระบบ|
|show mac address-table|Switch เรียนรู้ MAC ไหนใน VLAN/port ใด|
|ping|มีการตอบ ICMP จากเป้าหมายหรือไม่ ตาม policy และสภาพเส้นทาง|
|traceroute|เห็นการตอบกลับระหว่างทางอย่างไรตามวิธี probe และ policy|

**Running-config** คือการตั้งค่าที่ใช้อยู่ ส่วน **startup-config** คือข้อมูลที่เก็บไว้สำหรับเริ่มระบบ คำสั่ง `copy running-config startup-config` คัดลอกจากปัจจุบันไปเก็บ การสลับต้นทาง/ปลายทางเป็นคนละการกระทำ และพิมพ์ `show running-config` ไม่ได้บันทึกให้เอง

### 8.7 Up/Down กับวิธีตรวจอย่างมีหลักฐาน

`administratively down` โดยทั่วไปบอกว่า interface ถูกปิดทาง configuration ควรตรวจ `shutdown/no shutdown` ส่วน physical หรือ line protocol down ต้องดูชนิดลิงก์ สาย peer และการตั้งค่าที่เกี่ยวข้อง อย่าสรุปจากคำว่า down ว่า DNS ผิด

เริ่มทดสอบจาก PC ไป gateway ของตน → router ถึง router บน transit → ไป LAN ปลายทาง → ทดสอบบริการแอป หากขั้นไหนไม่ผ่าน ให้ตรวจจุดนั้นก่อน ไม่ลบ config ทั้งหมดเพื่อเริ่มใหม่โดยยังไม่รู้เหตุ

Packet Tracer **Simulation mode** ช่วยดูเหตุการณ์ ARP, ICMP และ protocol อื่นตามการจำลอง ใน ping ครั้งแรกบางสถานการณ์มีเวลารอ ARP จึงควรดู event และทดสอบซ้ำเพื่อวิเคราะห์ ไม่ใช้ความล้มเหลวครั้งเดียวสรุปทุกอย่าง **Check Results** ตรวจตามเกณฑ์ไฟล์กิจกรรม แต่ไม่ได้แทนการอธิบาย packet flow และเนื้อหานี้ไม่ใช่เฉลย topology ภายใน PKA ทุกไฟล์

**จุดหลอก:** คำสั่งผิดโหมด; ลืม no shutdown; ไม่บันทึก config; ชี้ next hop ผิด; มี route ขาเดียว; คิดว่า private LAN ต้องใช้ NAT ถึงจะ route หากันได้

## 9. เชื่อมทุกบท: เปิด HTTPS จากโน้ตบุ๊กผ่าน Wi-Fi หนึ่งครั้ง

### 9.1 สมมติข้อมูลเริ่มต้น

Notebook เชื่อม SSID `STUDY` กับ wireless router ได้ IP 192.168.10.20/24, gateway 192.168.10.1 และมี DNS server ที่ใช้งานได้ สมมติชื่อ `portal.example` resolve ไป 203.0.113.10 ตัวเลขปลายทางนี้ใช้เพื่ออธิบายเอกสาร ไม่ใช่เซิร์ฟเวอร์สาธารณะที่ให้ทดลองจริง

### 9.2 ขั้นที่หนึ่ง: เชื่อมไร้สายและได้ Configuration

Notebook ต้องผ่านการเชื่อมและ security ของ WLAN ตามโหมดก่อน แล้วจึงใช้ IP configuration เช่นที่ได้จาก DHCP ข้อมูลสองส่วนนี้คนละเรื่อง รหัส Wi-Fi ถูกไม่ได้ทำให้ DNS ถูกอัตโนมัติ และ IP ที่อยู่คนละวงกับ gateway อาจทำให้ส่งต่อไม่ได้ตามการตั้งค่าปกติ

### 9.3 ขั้นที่สอง: หาปลายทางด้วย DNS

Browser/ระบบตรวจ cache และถาม resolver ตามความจำเป็น เมื่อได้ A record 203.0.113.10 จึงมี address สำหรับการเชื่อมต่อไปบริการนั้น DNS ไม่ได้ส่งหน้า HTML กลับมาให้แทนเว็บ server

### 9.4 ขั้นที่สาม: เลือก Next Hop และสร้าง Frame

Notebook เห็นว่าปลายทางไม่อยู่ใน 192.168.10.0/24 จึงใช้ route ผ่าน gateway 192.168.10.1 ถ้ายังไม่รู้ MAC จะใช้ ARP resolve gateway **IP ปลายทางของ packet เป็น 203.0.113.10 แต่ MAC receiver/next-hop ของการส่งบนลิงก์ต้องสัมพันธ์กับ AP/gateway ตามโครงสร้าง Wi-Fi และการ bridge**

รายละเอียด address fields ของ 802.11 ต่างจาก Ethernet และอาจมีหลาย MAC fields จึงไม่ควรยัดภาพ Ethernet สอง MAC ลงทุก Wi-Fi frame ตรง ๆ หลักที่ต้องจำคือยังส่งถึง next hop บนลิงก์ ไม่ได้รู้ MAC ของเว็บ server ข้าม Internet มาใช้บน LAN

### 9.5 ขั้นที่สี่: Routing และอาจมี NAT

Router ส่งต่อโดยใช้ routing table และ longest prefix match หาก router บ้านตั้ง NAT/PAT สำหรับออก WAN จะเปลี่ยน address/port ตาม mapping ที่กำหนด IP ต้นทางที่ server เห็นจึงอาจเป็น address ฝั่ง NAT ไม่ใช่ 192.168.10.20 ส่วนรายละเอียด MAC เปลี่ยนตามลิงก์และ TTL ลดเมื่อผ่าน router

### 9.6 ขั้นที่ห้า: ตั้งการเชื่อมต่อ ปกป้องข้อมูล แล้วขอเว็บ

ในกรณี HTTPS บน TCP ทั่วไป client เชื่อม TCP ไป port 443 ด้วย handshake แล้วทำ TLS ตาม protocol ตรวจ certificate และสร้างบริบทปกป้องข้อมูล จึงแลกเปลี่ยน HTTP ภายในช่องทางนั้น ส่วน HTTP/3 ใช้ QUIC บน UDP จึงไม่ควรเหมาว่าเว็บทุกครั้งต้องมี TCP handshake

Server อาจตอบ 200, 404 หรือสถานะอื่น Browser อ่าน HTML และอาจต้องขอ CSS, JavaScript และรูปอีกหลายรายการ การเปิดเว็บหนึ่งหน้าอาจไม่ใช่ request เดียวหรือ connection เดียว

### 9.7 ถ้า Server อยู่ Cloud เรื่องไหนยังเหมือนเดิม

Client ยังต้องมีการเชื่อมลิงก์ IP, route, DNS และ transport/app protocol ตามบริการ ฝั่ง cloud อาจมี load balancer กระจายไปหลาย instances มี storage/database แยกส่วน หรือ auto scaling เพิ่ม backend แต่คำว่า cloud ไม่ได้ยกเลิกหลักเครือข่ายเหล่านี้

ปัญหาหน้าเว็บช้าอาจอยู่ที่ airtime ของ Wi-Fi, WAN, routing, TLS, backend หรือ database จึงต้องวัดว่าช้าตรงไหน แค่เพิ่ม VM ไม่ได้แก้ทุกคอขวด

### 9.8 ตารางไล่อาการก่อนเดาสาเหตุ

|อาการ|สิ่งที่ควรตรวจต้น ๆ|สิ่งที่ยังสรุปไม่ได้|
|---|---|---|
|ไม่เห็น SSID|Radio, coverage, ย่านที่รองรับ, การตั้ง AP|ยังไม่ใช่ปัญหา DNS|
|เห็น SSID แต่เข้าไม่ได้|Key, security mode, authentication/policy|ยังไม่ยืนยันว่า gateway ผิด|
|เชื่อมแล้วมี 169.254.x.x|DHCP และ IP configuration ในระบบที่ใช้ link-local|ยังไม่ยืนยันว่า AP เสีย|
|IP ถูกแต่ gateway ไม่ตอบ|ลิงก์ subnet/mask, interface, ARP และ ICMP policy|Ping ไม่ตอบไม่พิสูจน์ว่าปิดเครื่องเสมอ|
|เข้า IP ได้แต่ชื่อไม่ได้|DNS และชื่อที่ใช้ รวมถึงเงื่อนไขของบริการเว็บ|ไม่ใช่หลักฐานว่าสายเสีย|
|Ping ได้แต่เว็บไม่ได้|Port, TLS, firewall, HTTP และ server|ICMP ผ่านไม่รับรอง HTTPS|
|เว็บช้าเฉพาะตอนคนเยอะ|Airtime, bandwidth, queue, server load และคอขวด|ยังเลือกไม่ได้ว่าต้องซื้อ AP หรือ VM เพิ่ม|

### ลองตอบด้วยเหตุผลก่อนดูเฉลย

**1. เครื่อง A=192.168.5.100/27 มี network กับ broadcast อะไร?** ช่วงเพิ่มทีละ 32 คือ 0, 32, 64, 96, 128 ... เลข 100 อยู่ 96–127 ดังนั้น network = 192.168.5.96, broadcast = 192.168.5.127 และ usable = .97–.126 รวม 30 hosts

**2. ในตารางมี 172.16.0.0/16 AD 1 และ 172.16.8.0/24 AD 110 ส่งไป 172.16.8.20 เลือกอะไร?** เลือก /24 เพราะกำลัง forwarding จาก route ที่ติดตั้งแล้ว ต้อง longest prefix ก่อน ไม่เอา AD ข้าม prefix มาชนะ

**3. Switch รับ frame จาก MAC A ไป MAC B ที่ไม่รู้จัก ทำอะไรก่อน?** เรียนรู้ source A กับพอร์ตขาเข้า แล้ว flood unknown unicast ตาม VLAN ยกเว้นพอร์ตรับ ไม่เอา B ไปจำว่าอยู่พอร์ตรับ

**4. ใช้ SaaS แล้วลูกค้าต้องสนใจสิทธิ์แชร์เอกสารหรือไม่?** ต้องสนใจ เพราะผู้ให้บริการดูแลระบบแอปไม่ได้แปลว่าแก้สิทธิ์แชร์ที่ลูกค้ากำหนดผิดให้ทุกกรณี

**5. เพิ่ม AP โดยตั้ง channel เดียวกันและกำลังส่งสูงสุดทุกตัวช่วยให้เร็วขึ้นแน่นอนหรือไม่?** ไม่แน่นอน เพราะอาจเพิ่ม contention และ interference ต้องดู coverage, airtime และแผน channel จากสภาพจริง

**6. R1 มี route ไป LAN B แล้ว แต่ PC-A ping PC-B ไม่ผ่าน จะดูอะไรต่อ?** ตรวจ gateway ทั้งสอง PC, route กลับที่ R2, interface/link และ policy ที่เกี่ยวข้อง packet ไปถึงปลายทางยังต้องมี reply กลับถึงต้นทาง

### วิธีทำข้อสอบที่ช่วยลดพลาด

อ่านว่าถาม **ชั้นไหน** และ **อยู่ขั้นตอนไหน** ก่อน เช่น กำลังสร้าง routing table หรือกำลังส่ง packet ตรวจเงื่อนไขสำคัญ เช่น full-duplex, ไม่มี Auto MDI-X, subnet ปกติ หรือไม่มี NAT จากนั้นคำนวณด้วยหน่วยที่ตรงกัน และระวังคำว่า “เสมอ”, “ทุกกรณี”, “ทั้งหมด” ซึ่งมักลบข้อยกเว้นที่มีผลต่อคำตอบ

ถ้าผิด ให้จดเหตุผลเป็นประโยค เช่น “ใช้ AD ไปชนะ prefix ที่จำเพาะกว่า” จะช่วยแก้ความเข้าใจได้มากกว่าจดเพียง “ข้อ 15 ตอบ ค” แล้วท่องตัวอักษร
